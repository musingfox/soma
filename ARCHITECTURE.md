# soma architecture and plan

soma is a personal assistant core. It takes in what the interfaces send it, dispatches local coding agents to do the work, spends no tokens while it waits, and finally turns the results into a report.

The name comes from the cell body of a neuron: it gathers signals from the dendrites, integrates them, and sends them out along the axon.

Status: the code for M0 to M3.5 is on main (2026-10-18). The human acceptance runs with a real model, the Telegram phone client and the Google account finished on 2026-10-22; see the Notes on each obw task card. The external facts in this document were checked on 2026-10-18, and the citations were corrected after three independent reviews (Pi source, cc-mobile source, external docs).

Source abbreviations:

- **Pi paths** are under `packages/` of [earendil-works/pi](https://github.com/earendil-works/pi) at commit c268154. `spec` is `durable/docs/spec.md` and `README` is `durable/README.md`. A bare `types.ts` or `scheduler.ts` means `durable/src/types.ts` or `durable/src/harness/scheduler.ts`.
- **cc-mobile paths** are in `~/workspace/cc-mobile` at commit d9f0690.

## The problems to solve

1. **The messages agents give are too raw.** cc-mobile forwards to the phone what the agent itself said. The user wants a report that is put together across jobs.
2. **Letting agents monitor themselves on a timer is too expensive.** Every polling round is a model call, and a session has to be kept open the whole time.
3. **Each interface grows its own brain.** shikigami has its own brain (`brain.rs`, `backend*.rs`, `tools.rs`, `memory.rs`); cc-mobile has none. Adding Telegram would make a third one.

## Overall shape

```
           human-side interfaces              agent-side interfaces
  ┌──────────────────────┐            ┌──────────────────────┐
  │ Telegram (in-process)│            │ rex                  │
  │ web + desktop (M7)   │──▶ soma ──▶│ herdr                │
  │ terminal (dev)       │   core     │ native tty (M6)      │
  └──────────────────────┘            │ ACP; HTTP (later)    │
                                      └──────────────────────┘
```

- **The core is a long-running process.** It uses [Pi Durable](https://earendil.com/posts/pi-durable/) as its harness, with SQLite storage. One store can be owned by only one process, and the storage layer itself does not stop a second process (README:688). At startup soma takes chord's `processLock` on the realpath of the db's parent directory plus the file name (`chord/dist/manager.d.ts:66-72`, `acquireDbLock` in `src/core/harness.ts`); a second process prints `[soma] ...` and exits with status 1. After `kill -9` nobody listens on the old socket file, and the next process takes over (`chord/dist/manager.js:37-44`). But this checks first and then deletes the file, so it does not guard against two processes starting at the same moment. The socket file lives under `os.tmpdir()`, and moves to `/tmp/chord2-<uid>/` when the path is too long (`chord/dist/manager.js:69-80`). So two processes with different `TMPDIR` get two locks. When the launchd plist is written later, it must set `TMPDIR` to the same `getconf DARWIN_USER_TEMP_DIR` as the terminal.
- **Startup order.** After a restart the scheduler does not resume by itself. `harness.resume()` must be called first, or no background task and no queued input will move (`durable/src/harness/types.ts:716-720`). Next the event bridge reconciles once: it fetches herdr's `agent.list`, compares it with the dispatch list, and fills in the status changes that happened while the core was down. The acceptance of both M1 and M2 relies on this step.
- **All interfaces share one root conversation (`harness.root()`).** What you asked for on Telegram can be picked up again at the desktop. Each input marks its source with `entry.kind`, such as `chat.telegram` or `voice.shikigami`. The model cannot see `entry.kind`, only `content` (spec:2318-2320, README:427), so a source the model should know about must be written into the content.
- **The core produces one answer, and the adapter decides how to present it.** shikigami reads out a short version; Telegram sends text.
- **How answers are delivered.** The root conversation is shared, so every adapter sees every turn. The rule is: an adapter sends out only the answer of a turn started by its own `requestId`; reports are delivered through `notice` records; other turns are history only. This rule lives in the adapters, not in the prompt.

### Layers and dependency direction

Ports and adapters (shikigami already has this shape). There is only one goal: adding a new kind of interface means adding one adapter module, without changing the core.

```
  human-side adapters ──▶ HumanPort ──▶ core (domain + Pi Durable extensions) ──▶ AgentPort ◀── agent-side adapters
  telegram/ shikigami-socket/ terminal/                                         herdr/ rex/ acp/ http/
```

- **The core depends only on the types of the two ports.** It imports no adapter. Adapters depend only on the ports, do not import each other, and do not touch Pi Durable's types. Pi Durable's `Conversation`, `Entry` and `Harness` appear only inside the core.
- **HumanPort** is the actions of the "Human-side contract": submit, subscribe, notify, answer a prompt, and stop the running round. The core exposes soma's own event types (answer, failure, notice, dispatch status, whether a turn of the root conversation is running, the answer's text as it is written, a round the human stopped), not Pi's raw `watch()` events. In-process and out-of-process adapters get the same set of types; the only difference is a socket in between.
- **AgentPort** is the six actions of the "Agent-side contract", with status in the OSC 7501 vocabulary. Neither the port nor the core carries the name of any agent interface, so herdr, rex and ACP are just interchangeable implementations, and others can write one for their own terminal. The user picks one in the configuration. For how the implementations differ, see "How agent-side adapters differ".
- **Domain objects live in the core**: the dispatch list, the job state machine, and reports. They are plain TypeScript and do not know Pi Durable exists. The Pi Durable extensions are the layer that hooks them into the harness.
- **Test seams**: M1's `kill -9` acceptance uses a real herdr. The other unit tests use an in-memory fake AgentPort and fake HumanPort, and touch no socket.

What we do not build is a general plugin framework: no adapter registry, no dynamic loading, no configuration format reserved for interfaces that do not exist yet. The ports are two TypeScript interfaces, and the adapters are modules imported directly into `main.ts` and wired there.

### Two kinds of interaction must not mix

- **Talking to the assistant**: dispatching, asking for progress, reading reports. soma handles this part.
- **Operating a worker agent directly**: mirroring a session, answering permission prompts. This part does not go through soma's LLM; otherwise even one tap to approve would first need a round of model inference. When the model hands a permission prompt to the human, the human can answer it with a button in Telegram, and the core sends the answer straight to the agent (see "Answer a prompt"). Mirroring a session and other direct operation are handled by the terminal's own client, not by soma. On 2026-10-18 cc-mobile's herdr passthrough handled this part; from 2026-10-24 cc-mobile is no longer needed (see "Decisions made").

### Compacting the root conversation

The root conversation is shared by all interfaces and never ends. pi-durable compacts on its own, counting down from the model's context window: a request waits for a compaction above `contextWindow - reserveTokens`, and one starts in the background `backgroundTokens` below that (defaults 16384 and 32768, `node_modules/@earendil-works/pi-durable/dist/harness/agent.js:10-15`, checked in `dist/harness/generation.js:306-316`). On the root model's 1,000,000 token window those defaults wait until about 950 thousand tokens, so before 2026-11-18 the root, at about 247 thousand, had never been compacted, while a request that rewrote the prompt cache cost about 0.15 USD at that size. The human decided on 2026-11-18 that the host compacts at a threshold, not the model, at 100 thousand tokens, keeping about 20 thousand verbatim (card `root-compaction-dev`). In this section `pi-durable/README.md` means the 1.5.0 file in node_modules.

- **Where it is set.** The config's `compactAt` (`SOMA_COMPACT_AT`), a positive integer of tokens, 100000 by default (`src/config.ts:56`). At startup `rootCompaction` (`src/core/harness.ts:55`) takes it with the root model's context window from pi-ai's catalog (`models.getModel("anthropic", model)`, `src/main.ts:135`) and passes pi-durable a `settings.compaction` with one `modelOverrides` entry for that model: `reserveTokens` is the window less `compactAt + 32768`, `backgroundTokens` 32768 and `keepRecentTokens` 7000. pi-durable counts what it keeps at 3.5 characters a token (`dist/harness/compaction.js:229`), and on prod's mostly Chinese root an estimate of 20000 measured 54 to 67 thousand real tokens, which with the summary and the restated tools would put the context back at `compactAt` at once; 7000 is about the 20 thousand real tokens the human decided on. So a compaction starts in the background once the context passes `compactAt`, and a request waits for one once it passes `compactAt + 32768`; on a 1,000,000 window with the default that is 100000 and 132768. The entry is for the root model only: a reserve fitted to a 1M window would make every request on a smaller model wait. pi-durable reads the window and the entry at each request (`dist/harness/generation.js:48,90`, `dist/harness/compaction.js:201-210`), and the entry is keyed by the config's `model`. A root keeps the model stored in its `pi.agent` document from when it was made (pi-durable `harness.root` applies `agent` only then), so if that ever differs from the config's `model`, no entry matches, pi-durable's defaults apply and nothing reports it; on 2026-11-18 prod's root and config both name `claude-haiku-5-5`.
- **When the window is too small.** When `compactAt + 32768` is not below the window less 16384, or the catalog does not know the model, soma passes no compaction settings and pi-durable's defaults apply unchanged.
- **What the model sees after it.** pi-durable summarizes the entries before the cut with its own prompt (`dist/harness/compaction.js:12-47`); soma adds nothing to it. The summary goes into one `pi.compaction` entry whose head is the first entry kept (`pi-durable/README.md:608`). On the next request the prompt planner (`dist/harness/prompt.js:56-64`) writes one system entry holding every section and every tool once, and omits every earlier `pi.system` entry, also those among the entries kept. A compaction thus restates what the model can do by itself, and soma writes no line of its own about the tool set (a visible line on a tool change is a later milestone). `test/compaction.test.ts` drives this through the real core on the faux model.
- **The summary is not a turn.** It is made while the conversation keeps running and is placed when the conversation is idle or at the next turn boundary, so it does not count toward the wake-ups in the "Scheduled digest" section.
- **Reading old records is not affected.** Older entries stay in storage. `inspect`, `recall` and `mark_denied` scan storage with `tx.scanEntries`, and reflection reads the fact layer's documents (`src/core/extensions/reflection/index.ts:66`); none of them goes through the context the model sees. Notices carry no model message, so they never were in the model's context; job questions, long-term memory and the interfaces are sections, restated after the summary. What only the transcript holds, such as the question of an `ask` whose press comes back as its bare label, or a wake's fingerprint, the model keeps only as far as the summary does.
- **Cost.** The cost of a summary is recorded in the `pi.usage` document (`pi-durable/README.md:640`, `dist/harness/compaction.js:144`), not in an assistant entry. `inspect`'s `usage` sums only assistant entries (`src/core/extensions/inspect/index.ts:75-95,190-196`), so it cannot find the cost of compaction.
- **Failure.** When a compaction that a turn waits for at the blocking threshold fails, the turn fails too, and the input ends as `unanswered` with `model_error`, `Compaction failed: <error>` (`pi-durable/README.md:642`). This takes the usual failure path: HumanPort emits a `failure` event and records an outcome signal, and `inspect`'s `failures` can find it. A background compaction that fails leaves the next request to go ahead; its error stays in `docs["pi.live"].compactionFailure`.
- **Not yet run on prod.** prod's config sets no `compactAt`, so the default takes effect there at the first release with this code, which is the next milestone's decision. The first run against the real model is the dev one the card asks the coordinator for.

### Event bridge: monitoring costs no tokens

The event bridge sits outside the harness. It subscribes to herdr's events and decides what to do with rules, without calling the model:

| Event | Handling | Wakes the model? |
|---|---|---|
| Agent stuck (blocked) | Submits an `input` to the root conversation with `requestId` `agent:<agent>:<seq>`, unless its prompt is the one last handed over (see the seq point below) | Yes. The model decides whether to answer for the agent or hand it to the human. `kind=auth` is the exception: the model is not woken, and the event bridge writes a `notice` (question) to the human in the same commit that records the seq, and records an escalated judgement. Each judgement and its reason are written into the dispatch list and listed in the digest, so the human can check its judgement afterwards |
| Agent finished (enters idle or done) | Recorded once per transcript end: a turn whose transcript's last record is the one already recorded is not recorded again (see the seq point below). Written into the dispatch list with `conversation.commit`, with a record appended. If the outcome is `需要你` or `失敗`, or it is `完成` and the human picked an option or replied on this job in person within ten minutes, the same commit writes a `notice` to the human whose content is the agent's reply verbatim; `需要你` uses question and the rest use report (`urgent` in `src/core/domain/report.ts`). A `需要你` reply that ends listing options in the launch rules' form is told without the list, its options going as the question's buttons (see "Options a job's agent lists") | No |
| User asks on their own | The adapter submits an `input` | Yes |

The event bridge is in the same process as the harness, just not in the LLM loop; it needs to call `conversation.commit` directly.

Checked grounds:

- **Neither `write` nor `commit` starts a turn of inference.** The source is the spec of pi `packages/durable`, spec:2343-2355 and README:421. The exception is when the conversation is idle, the inbox still has queued items, and the write is not display-only; then one more turn runs (spec:2363-2367).
- **`requestId` is deduplicated across the whole conversation** (spec:2358). The root conversation is shared, so each source needs its own prefix: `agent:<agent>:<seq>`, `telegram:<msgid>`, `digest:<until>`.
- **herdr's event stream alone is not reliable.** cc-mobile also fills gaps with `session.snapshot`, and uses `state_change_seq` to tell whether the state really changed. The timer ticks once a second, but the snapshot rate depends on the listener tier: once every 1, 3, 5 or 30 ticks (`server/herdr/pane-events.ts:77, 94-98, 436-458`). The event bridge must do the same. So monitoring costs no tokens because code polls, not because of event push alone.
- **The first prompt of a dispatch is sent by the event bridge, not right after `agent.start`.** Tested against herdr 0.9.5 on 2026-10-18: right after `agent.start` responds, `agent.prompt` returns `agent_not_ready`; putting the prompt in claude's launch arguments is rejected by herdr with `invalid_agent_argument`; in a new repo claude first stops at the folder-trust dialog (herdr reports blocked). So the dispatch tool only stores the prompt (cc-mobile's rules from `server/launch-prompt.ts` plus the card content) on the job, and the event bridge sends it the first time it sees the agent enter idle. If it sees working or done, it drops the unsent prompt, because that means someone has already given the agent work; this also avoids resending after a crash and restart.
- **seq names an observation; it does not count transitions.** Every status an agent-side adapter reports carries a seq, with one rule for every adapter (`src/ports/agent.ts`): the same value is the same observation, and a new value does not promise the agent went through a transition. herdr sends its `state_change_seq`; rex sends the root record's `updated_at` in microseconds since the epoch, parsed from the timestamp's full fraction (rex reports to the microsecond, e.g. `2026-10-26T23:23:54.388938+08:00`), not `Date.parse`, which keeps milliseconds and would merge two reports within one; it is stable for one report, since rex re-sends `program_status_changed` whenever anything in the record changed. The dispatch list keeps the last seq each job handled, and an observation carrying that seq again (a repeated snapshot, a listing with a seq at the reconciliation after a restart) does nothing. A new seq acts only on what changed (`src/core/domain/bridge.ts`):
  - **blocked** wakes the model (or escalates, for `kind=auth`) unless its prompt is the one last handed over. The job stores the `fingerprint` and `msg` of the block it last handed over (`Job.handedOver`), in the commit of the seq that woke the model or escalated, and forgets it when a status other than blocked is folded in, by the bridge or by the reconciliation. A blocked observation whose fingerprint and msg match the stored ones only records the seq. The rule does not compare against the job's stored status, because that status is not always one the bridge handed over: the reconciliation after a restart writes it straight from `list()`, and herdr's listings carry no seq, so they never go through the bridge; the dispatch tool writes the listed status of an agent it found already running. A block that first appeared while soma was down, or a trust dialog a rerun dispatch found, is therefore handed over at the first snapshot that reports it.
  - **done or idle** after a turn reads what the agent's transcript ends on (`readResult`, M5-2d). A completion's identity is the transcript's last record, whoever wrote it: `AgentResult` is `{ id, text? }`, where `id` is the `uuid` of the conversation's last record that carries one, the user's prompt, a tool result or the assistant's reply, and `text` is the final reply, present only when the transcript does not end awaiting one (`readLastRecord` in `src/agent-cli/transcript.ts`, which herdr and rex share). `complete` records a finished turn only when that id differs from the one the job stored with its last recorded turn (`Job.resultId`), or none is stored yet; the outcome comes from `text`, and a transcript that ends without a reply, an interrupted turn or one ended by a denied permission, is recorded with outcome `未知` under its own last record. A transcript that cannot be read at all, or holds no record with an id, is still recorded with outcome `未知` and leaves `resultId` alone. So a re-reported done or idle is recorded once, whether the turn ended on a reply or on the user, and a second turn between two samples, with no working seen in between, is recorded because its last record is new. Checked against real transcripts on 2026-10-27: `uuid` is on every `user` record, tool results included, and every `assistant` record (one per content block), but also on the `system` (`turn_duration`, `stop_hook_summary`) and `attachment` records claude writes after a turn; those, and the sub-agent, injected and compaction records, are not counted, since one written after the turn was read would name a second turn. Before M5-2d the id was the last assistant message's `message.id`, and every undefined read was a new turn: a turn that ended on the user recorded another `未知` turn at each re-stamp of its idle or done (about 40 of 600 recent transcripts ended on a user record).
    Accepted edges (accepted by the human on 2026-10-27). (a) A turn claude has not written at all when rex's `replyMs` (2 s; see "The rex implementation") passes is not recorded at its end: the read at the timeout returns the turn before's last record, which the job already holds. It is recorded at the re-check 10 s later (below), or at a later re-stamp, read at once. (b) A final reply split over a thinking record and a text record, read between the two, records `未知` under the thinking record's id and then the real outcome under the text record's, since claude writes one record per content block, each with its own `uuid`. Such a read happens where nothing waits for the reply: herdr's, the startup reconcile, and rex's when the watch does not know the turn's end. rex's wait for a known end does cover it: a last record holding only thinking counts as the reply not yet written (`awaitingReply`), so the wait goes on until the text is out or 2 s pass. The slow-flush cases, accepted by the human on 2026-10-27 with the re-check as their recovery: a session's first turn read before its transcript exists (`undefined`, recorded without a reply id), a turn only part written at the timeout (its prompt but not its reply, recorded under the prompt's id), and a reply whose text is written more than 2 s after its thinking (recorded under the thinking record's id) each record `未知` and then the real outcome, at the re-check 10 s later or at a rex re-stamp. A turn still unwritten at the re-check stays recorded as `未知` until a re-stamp; the next digest reads the reply into its report, without changing the recorded outcome. The re-check (M5-2f, rex only): when `readResult` returns because `replyMs` passed, whatever it returns, the adapter re-reads the block's root `program_status` record `recheckMs` (10 s) later, through the watch's queue, so it is ordered with real reports. It reports again when, since that read, the watch has reported no `working` and no `blocked` for the block (only done, idle or error, under any `updated_at`), the block is still in the hangar, claude is in the foreground, and the root record is now done, idle or error; it emits that record's status under the block's last emitted seq + 1. A done that settled into idle before the re-check is the usual end of a turn, and the re-check reports the idle. `track` takes the report as one with no `working` seen, so `turnEnded` is cleared and the next read is at once. The core reads where it reads for any report: at a done after a done or an idle, and at an idle after an idle; there a new last record records the real outcome, with its notice as for any completion, and the same id records nothing. A re-emitted idle after a done the core holds reads nothing, and the turn is read at the real idle event that follows, without waiting; a re-emitted error never reads. If that idle event is lost (a transient non-claude foreground, a payload failing its schema), only a re-stamp or the next turn recovers the turn. A block that went on to work or to a prompt gets nothing, since the watch reported the end of the turn after it, as does a block closed, left by claude, or whose record is working or blocked by then. The contract author amended this rule on 2026-10-27; the first M5-2f build required the root record to be the very one the watch last reported, same state and `updated_at`. One re-check is pending per block, a newer timeout replacing it, and closing the watch (the last `onStatus` unsubscribed) cancels them. Neither AgentPort nor the core changed. A job whose `resultId` was stored before M5-2d is an assistant `message.id`, which no record uuid matches, so it records one extra completion at its first observation after the upgrade; prod had not been released with `resultId`, so there is no data migration.
  - The wake's input is submitted before the seq and the handed-over prompt are committed. A crash between the two leaves the job as it was before the block, so the redo on restart wakes again under the same seq, as long as the adapter reports the same seq for the same observation, and the same `requestId` returns the first submission. An escalation has no side effect before its commit, so a crash before it simply redoes it.
- **Accepted edge: a repeated question is missed when nothing was observed in between.** If an agent is answered and then asks the identical question again (same fingerprint and msg) while no status other than blocked was observed in between (for herdr, both transitions within one poll), the model is not woken for the second ask. Any observed non-blocked state in between, working included, whether by the bridge or by the reconciliation, makes the next block wake the model again. Detecting this case would need a transition counter, which rex does not have and an adapter cannot keep across a soma restart.
- **The notice that an agent is stuck uses `whenBusy: "followUp"`, not `steer`.** While soma is running a turn, the notice waits until the whole turn ends (`src/core/extensions/dispatch/bridge.ts:69`): pi-durable 1.3.0 takes followUp items only at the final boundary of a turn, while steer items are taken at the end of every tool round (`node_modules/@earendil-works/pi-durable/dist/harness/inbox.js:45`). steer is not used because it shares the answer with the turn already running: a steer input is added to the same turn (`dist/harness/generation.js:538-539`), and when a turn ends every input settles to the same `answer` (`dist/harness/live.js:27-30`). This has three consequences. Merged into a turn the user asked on Telegram, the answer the phone receives carries the answer given for the agent, and is no longer the one answer per turn that the "How answers are delivered" point requires. Merged into the digest turn, the digest task writes the answer given for the agent into the report notice (`src/core/extensions/digest/index.ts:142-147`). When the merged turn fails, HumanPort emits one failure per input (`src/core/human-port.ts:78`), so the human gets the failure reply of their own turn plus a second one that `agent:` pushes through `PUSHED_FAILURES` (`src/ports/human.ts:16`). steer only saves the wait for the turn to end, which does not pay for these costs.

### Idempotent dispatch

Dispatch goes through the herdr adapter (the decision on open question 1), and the agent name is the card name. Tested against herdr 0.9.5 on 2026-10-18: as soon as `agent.start` responds, `agent.list` lists the name (`launch_pending: true`); a second `agent.start` with the same name is rejected by herdr with `agent_name_taken`. Therefore:

- The dispatch tool first stores the session id with `api.memo` and then passes it to `agent.start`, because herdr cannot read it until claude reports `agent_session`.
- A rerun first checks whether the dispatch list has the card, then whether `agent.list` has an agent with that name. It starts the agent only if neither has it.
- The dispatch list is written in a separate `api.commit` before the tool result; the harness commits the tool result, and the two cannot be merged. The remaining gap is "`agent.start` has responded, the dispatch list is not written yet"; a rerun finds the agent with that name in `agent.list` and does not restart it. `npm run smoke:dispatch` hits exactly this gap.
- On a crash "after `worktree.create`, before `agent.start`", the rerun uses `worktree.open` to reopen the same worktree.
- `soma dispatch` takes the same steps from host code, with the session id stored in a document instead of a memo, and the human's rerun in place of the tool's replay; see "Decisions made", 2026-11-17.

### Scheduled digest

It is a background task, created with `tx.createTask(T, input, { ownership: { kind: "conversation" }, background: true })`. It wakes every ten minutes and first reads the dispatch list. If no job has newly finished since the last digest, it only advances the checkpoint and does not wake the model. If some have, it submits one input asking the model to write a short report. So a finished job is reported within ten minutes at the latest, and the model is woken only when there is something to report. Jobs the event bridge has already notified about right away are not listed in the digest again, and when only such jobs are left, the model is not woken either.

- **`sleep(until)` itself is not stored.** It is only a timer in memory. The wait survives a restart because `until` is written in the checkpoint: after a restart the task goes back to pending, the phase reruns, and it returns at once if the time has passed (types.ts:240, scheduler.ts:1816-1827, spec:1930).
- **Every round must advance the checkpoint, or the task is judged faulty** (spec:1919-1921). Within one phase, any change to the checkpoint's content counts as advancing, so a single `tick` phase that moves `next` forward and adds one to a counter each round is enough; it does not need two phases (`durable/test/examples/13-recovery.ts:21-47` is written this way).
- **The model is woken only when the time comes.** The task submits an input to the root conversation (`runtime.conversation(id).submit`) with `requestId: "digest:<until>"`; otherwise a crash between the submit and the checkpoint would submit twice. A background task can start a turn on its own idle conversation; the example is at `durable/test/examples/23-subagent-background.ts:108-116`. The model reads the jobs in the dispatch list that finished during this period and writes one report.
- **"Newly finished" goes by the event bridge's completion records.** The task reads the `soma.dispatch.done` records in the root conversation, and the checkpoint stores the id of the last record already reported. It does not judge by the dispatch list's `seq`, because the wrap-up from done to idle also gets a new seq and would be reported again.
- **Pin the range before submitting.** Before submitting the input, write into the checkpoint which record this digest covers up to. Otherwise, on a rerun after a crash, jobs that finished in between would be counted in the range, but the resubmit is deduplicated, the report would not have them, and they would go unreported.
- **The report and the next checkpoint are in one commit.** The task waits for the turn to be answered, writes the answer as a `notice` record, and commits it with the advanced checkpoint, so wherever a crash happens there is only one notice. When the model's turn fails (for example, no API key), the notice carries the raw job list instead, so the jobs of this period are not left unseen.
- **There is no built-in cron.** `sleep(until)` is the only timing primitive (types.ts:240).

The number of model wake-ups a day is about "times stuck + ten-minute windows with newly finished jobs + times the user asks on their own", independent of how long jobs run. Compacting the root conversation makes its own summary calls, which do not count as wake-ups; see "Compacting the root conversation". Each wake-up is one turn (run), and a turn has several model requests, because tool calls take a few more rounds (spec:2335-2338).

### Agent-deferred instructions

Decided with the human on 2026-11-04 (cards `agent-defer`, `agent-defer-reclaim`, `agent-defer-resume`, `acp-agent-adapter`). An agent soma dispatched hands soma an instruction and a time, and at that time soma's host code sends the instruction straight back to that agent. `schedule` does not fit, because it wakes soma's model at `at` and has no way to reach an agent. So this is the one channel from agents into soma, and it is not part of AgentPort, which only goes from soma outward.

- **Ingress.** `bin/soma defer --at <when> "<instruction>"` (`src/defer-cli.ts`) sends one JSON line over a unix socket (`src/adapters/defer-socket/`); `defer()` in `src/core/extensions/defer/` checks the card against the dispatch list and creates the task in the same commit. MCP was rejected: every agent can already run a shell command, and a CLI needs nothing installed per agent.
- **Identity is the card, set by soma at start.** The rex adapter types the launch line with `SOMA_AGENT=<card>`, `SOMA_SOCKET`, `SOMA_NODE` and soma's own `bin` first on `PATH`, so an agent started by a release calls that release's CLI. Nothing authenticates `SOMA_AGENT` beyond the socket's 0600 mode, so any process of the same user can name any card.
- **At most once.** The task commits a `sending` checkpoint before `prompt` and the terminal state after it. A rerun that finds `sending` does not prompt again; it writes one notice that the instruction may not have arrived. A duplicated instruction can do harm ("run the migration"), while a lost one is recoverable once the human knows, which is also the rule for the response tools. A prompt is retried (30 s, up to 20 times) only on `PromptRefused` (`src/ports/agent.ts`), which an adapter throws only when nothing was typed; any other error is treated as the crash window.
- **Every other ending is one notice:** the agent no longer listed (`gone`), the crash window or a post-paste error (`unsure`), retries used up (`failed`). Nothing is submitted to the root conversation. A deferred turn's completion is still reported by the next digest, like any agent turn.
- **The HumanPort opens before `harness.resume()`** (`src/core/startup.ts`). It passes on only commits made after it attaches, and a deferral due while soma was down commits its notice as soon as tasks resume; opened later, that notice was stored but never pushed. The digest and reflection notices at startup had the same gap.
- **Reclaim.** An agent with a pending deferral holds no hangar slot: soma stops it (`AgentPort.stop`: rex `block.close`, ACP `session/close` and ending the process) the first time it sees the agent idle or done at or after the accepted defer. The state is `Job.reclaim` in the dispatch list, not in the deferral doc, because "stopped on purpose" must outlive the deferral so that no later reconcile reports the agent as vanished. Phases:
  - `due` is set in the commit that accepts the defer. The bridge (after an idle or done), `defer()` (agent already at rest) and the startup reconcile try the reclaim; each re-lists the agent first and leaves a `working` or `blocked` one alone. `due` to `stopping` is a compare-and-set, so only one of them stops it.
  - `sending` holds the job while a deferred prompt may go out, so a send and a stop never both proceed. Afterwards the job is `due` again only if another deferral of the agent is pending; a normal send does not reclaim at once, because just after a paste the listing may still show idle. Only a crash-rerun that releases the job reclaims, and it waits for the startup reconcile so the two cannot stop it twice.
  - `stopping` is committed before the stop and `stopped` after. At restart a listed `stopping` agent is stopped only if a deferral is still pending, else the job is disarmed; a deferral meeting `stopping` says the stop may not have gone out.
  - A stop that fails while the agent is still listed ends `failed` with one notice and is not retried. `reconcile` never turns a `stopping`, `stopped` or `failed` job into a vanished one, and the bridge ignores statuses of a `stopped` job.
  - A `stopped` agent that runs `soma defer` is open again (its window reopened, or a resume whose start timed out came up), so `defer()` arms it `due`, but only when a listing taken before the commit shows it; an unlisted or unlistable agent stays `stopped`, so a stray defer cannot lead a restart to report it vanished. A stop committed between that listing and the commit would leave a gone agent armed, so after a commit that moved the job from `stopped` to `due`, `defer()` lists again and, if the agent is absent, moves the job from `due` back to `stopped` in a new commit, only while it is still `due`; a second listing that fails leaves the job as it is.
- **The digest tolerates a reply it cannot read.** A reclaimed window is gone by the next digest; one job's failed `readResult` used to fault the digest task for good. Now that job is reported without its reply. rex reads a closed window's transcript through the session id it last saw on the block label, within the same process only.
- **Resume.** A deferral that falls due while its agent is gone (reclaimed, or closed by hand) starts it again with `AgentPort.resume`: rex opens a new hangar window typing `claude --resume <session id>` with the dispatch's launch environment, ACP starts a new process with `session/load` (see "The ACP implementation"), each past the hangar cap, and only a resume skips the cap. A plain `--resume <id>` keeps the session id and appends to the same transcript (checked with `--print` on Claude Code 2.1.318, and in rex by the smoke). The window's directory is the first absolute `cwd` in the session's transcript, because the job stores no worktree path and claude finds a session by its directory; it goes to rex as an option, never into the typed line.
  - The task's phases are `wait`, `resuming` (starts only an agent not listed), `ready` (polls the listing until the agent is idle or done) and `sending`. The dispatch's way of sending a first prompt is not reused, because the bridge pastes with no commit before it and a crash there could resend.
  - The job's reclaim is `resuming` while a deferral holds it; the reclaimer leaves it alone and the bridge takes the new window's statuses. If the agent turns out gone, the job gets back the reclaim it had before, so it is `stopped` only if soma stopped it. A `resuming` hold whose task is no longer live is released when that agent runs `soma defer` again.
  - A failed listing is doubt, never "not listed": it never starts a second window and never ends a deferral as closed. If listings still fail one `readyMs` past the ready deadline, the deferral ends with one notice naming the error and saying the agent may be running. A notice says soma started the agent again only when `resume` returned.
  - herdr and tty throw the port's `NotImplemented` for `resume`, and their deferrals end `gone` with the old notice. So does ACP for the one agent it cannot start again, one with no session recorded or no transcript of it. Any other error ends the deferral `unresumed`, with a notice naming it.
- **Scope now.** rex and ACP: herdr's adapter does not implement `stop` or `resume`, and tty's does not implement `resume`. One-shot only.

### Where reports get their data

Reports read the worker agent's transcript, not the terminal screen.

- **The transcript file can be found.** At dispatch claude is started with `--session-id <uuid>`, so the transcript file is at `~/.claude/projects/<cwd with non-alphanumeric characters replaced by '-'>/<uuid>.jsonl` (cc-mobile `server/transcript/path.ts:56-58`). When the encoded path misses, `path.ts:90-101` scans the whole projects directory for it.
- **The reading logic can be reused.** cc-mobile's `server/transcript/reader.ts` reads incrementally by byte offset; `records.ts:96-123` keeps only the user and assistant record types.
- **"Extract the final answer" must be written ourselves.** cc-mobile has no such function (not confirmed by a search of the whole repo). The approach is to take the last assistant message after the agent finishes. cc-mobile's dispatch prompt (`server/launch-prompt.ts`) asks that the first line of the reply say `結果：完成／需要你／失敗`, and soma can parse this line directly to classify it.

### Basic assistant abilities

Besides dispatching agents, soma itself needs an assistant's basic abilities: reading email, checking the calendar, memory, and handling work at a set time. The principle is that the core has no dedicated code for any one ability:

- **Scheduling.** "Handling work at a set time" and the scheduled digest use the same mechanism: the model calls the `schedule` tool, the core creates a background task that sleeps until the set time, and then submits the instruction back to the root conversation as an input. The wait holds no session and spends no tokens; recurring tasks advance the checkpoint every round. The schedule list is stored in a document, and the model can list and cancel entries.
- **Email and calendar.** MCP servers come in through the pi-mcp bridge; soma only hooks the MCP tools into the harness. Gmail and Google Calendar use workspace-mcp, with credentials in `~/.config/soma/` outside the repo (the decision on open question 5). To the model these are tools just like the dispatch tool; the only difference is that they are not rerunnable (sending mail cannot be replayed).
- **Web search and page fetch.** Two core extension tools, `web_search` (Exa) and `web_fetch` (Defuddle), under the read-only exception decided on 2026-10-27 (see "Decisions made").
- **Memory.** See the next section. Because reports and scheduling both use it, memory moves up to M2.

### Memory: porting shikigami's design

Rebuilt with Pi Durable's components, following the rules in the "Persistent state" section of shikigami's `ARCHITECTURE.md`:

- **The curated layer** maps to a section, rendered into the system prompt before each request. Trust is decided line by line: lines the user wrote are trusted as is; lines the model wrote get an audit prefix, are placed inside a fence, and are marked unconfirmed. A write over the budget is refused; no content is ever truncated.
- **The curated layer can be revised.** It is the behavior layer, and soma may change it directly (the user's decision on 2026-10-18). To change code, soma opens an obw card and dispatches it into fleet; soma cannot merge anything itself. Each line has a number issued by a counter, rendered as `[#<id>]`, and a deleted number is never issued again. The model rewrites with `revise_memory`, deletes with `forget_memory`, and restores any version that `memory_history` lists with `restore_memory`. The rules:
  - Every revision must carry a reason and at least one evidence id, or it is refused, and the reason for the refusal goes back to the model as the tool result. Only the format is checked, not whether the evidence exists, because Pi Durable has no API to read a submission by id.
  - The text before the change, the revision time, the reason and the evidence are stored in the same document's `history`, in the same commit as the change. History does not go into the system prompt and does not count toward the size limit; the limit counts only the lines that exist now.
  - A line the model rewrote always counts as written by the model, even if the original was the user's, so it gets the audit prefix and goes into the fence. A restore puts back exactly what was stored, so the user's original text still counts as the user's after a restore.
  - Every revision writes, in the same commit, a `notice` with `data.kind: "report"` to the human, stating which line changed, the text before and after, the reason and the evidence. It is not merged into the ten-minute digest, because a wrong memory affects answers from the next turn on, and the human should see it at once.
- **Evidence ids.** Every item the self-inspection tool returns and the evidence a memory revision cites use one format: `entry:<EntryId>`, `submission:<SubmissionId>`, `task:<TaskId>`; or `document:<DocumentId>@<Seq>` for the version of a document at a given commit (Pi Durable has no separate document revision record; a version is fixed by the document id and the commit sequence number); or `decision:<card>#<n>` for the n-th answer-for-the-agent or hand-to-the-human decision on a card in the dispatch list (counted from 0). The dispatch list is `history: "latest"`, so old versions cannot be read back, and a decision therefore cannot be cited with `document:`; decisions are only appended, so their numbers never change. The numbers are all Pi Durable ids (`durable/src/types.ts:27-36`). The regex that checks them is `EVIDENCE_ID` in `src/core/domain/memory.ts`.
- **The fact layer** maps to a document. Code writes it; nothing goes through model extraction.
- **Outcome signals** are stored in the fact layer, with kinds starting with `signal.` (`src/core/domain/signal.ts`), for self-inspection and reflection to judge which behaviors should change. Each carries a key, and one key is recorded only once, so a write rerun after a crash is not duplicated. The event bridge records two kinds in the same commit that records the seq: a prompt stuck again on the same fingerprint within ten minutes after an answer for the agent, and a dispatch whose outcome is a failure or whose outcome line cannot be read. HumanPort records one when it sees a turn end as `unanswered`. When the user rejects the previous turn, the model marks it by calling `mark_denied`, and the record points at the answer entry of the rejected turn; the description is produced by code, and the model's words do not go into the fact layer.
- **`recall`** is a tool that searches old conversation records. It costs nothing unless it is called.
- **`inspect`** lets the model query its own execution trace, read-only: failed turns, tokens and cost per turn, answers for the agent and hand-offs to the human, and the last status of each dispatched card. Every item it returns has an `evidence` field, in the format of "Evidence ids" above. Over the item limit, it returns only the newest items and states the total.
  - In pi-durable 1.3.0 neither `Tx` nor `Session` can scan submissions, so this tool scans with the Harness's own `Storage`, and only inside an `api.commit` callback: the callback holds the Session's commit line, so it cannot read a half-committed state, the same as reads through `Tx`.
  - The evidence for each dispatched card is its completion record (the `soma.dispatch.done` entry); for a card not yet finished, the evidence is the `dispatch` tool result entry that recorded the job. The dispatch list itself cannot be read back at old versions, so it is not cited with `document:`.

### Reflection

Once a day soma reads its own outcome signals and improves itself (`src/core/extensions/reflection/`). Its permissions follow the 2026-10-18 decision: it changes the behavior layer directly, opens a card and dispatches it to change code, and merges nothing.

- **It works like the scheduled digest**: the background task's checkpoint stores the next time and how far into the fact layer it has read (the fact layer is append-only, so a position serves as the cursor); the range is pinned before the submit; and the model's answer is written as a `notice` in the same commit as the next checkpoint. It does not use a reminder task from the `schedule` tool, because that always wakes the model when the time comes. The `requestId` is `reflection:<until>`, and adapters do not push this turn separately, for the same reason as `digest:`.
- **With no pending signal, the model is not woken.** Pending means the `signal.*` records after the cursor, minus the problems already handled.
- **One problem goes to the model only once.** Each signal is assigned to a problem. One with a card goes by the card. A failed turn goes by its failure cause: the reason plus the detail, with uuids, long mixed alphanumeric ids and numbers of five or more digits erased (`failureCause` in `src/core/domain/signal.ts`), so two 401s are one problem and a 401 and a 429 are two. Every other signal is its own problem. A problem counts as handled once its evidence has been cited by any memory revision or by a card reflection opened. This is a rule in code; it does not rely on the model remembering.
- **When a handled problem shows up again, the human is told and the model is not woken.** It means the earlier handling may not have worked, and having the model revise or open cards again tends to make things worse. So code writes a `notice` to the human, stating the problem, the earlier revisions or card, and the evidence ids of the new signals. The notice and the cursor advance are in the same commit. Each revision or card is notified at most once (those already notified are recorded in the reflection document's `alerted`). If a new revision or a new card is made for the problem later and the new handling does not work, the human is told once more.
- **Signals become evidence ids.** A signal of being stuck again after an answer for the agent has no entry of its own, so its refs also record the number in the dispatch list of the answer that did not work, cited as `decision:<card>#<n>`. A failed turn is cited with `submission:`, and the others with `entry:`. Reflection's input also lists every answer-for-the-agent and hand-to-the-human decision of the related cards, so the model can cite the whole chain.
- **To change code**, the model calls `open_card`, which opens a todo card in the obw project of soma's own repo. The same tool then dispatches the card into fleet (sharing `startJob` with the `dispatch` tool) and notifies the human. When the dispatch fails, the tool result tells the model the cause, and the notice states that the card stays at todo. Both steps are in one tool so the model cannot open a card and forget to dispatch it. Cards are created by the obw pm convention: `create template=task`, setting one property at a time. Two things were tested against the obsidian CLI on 2026-10-19. First, with a template, `content` is ignored, so the body must be written by reading back the filled template and then `create overwrite`. Second, `create` on a path that already exists does not fail; it creates `<card> 1.md` instead, so `read` first to confirm the path does not exist. The card body records the tool call's call id, so on a rerun after a crash the tool recognizes the card as one it opened.
- Smoke tests: `npm run smoke:reflection` runs `kill -9` once while waiting and once during the reflection turn; `npm run smoke:reflection-card -- <repo>` opens and dispatches a card with a real obsidian and a real herdr, then deletes the card, the worktree and the branch.
- `open_card` is reflection's tool only. Its description says so and sends a ticket the human asks for to `dispatch`; its evidence check is not relaxed.

### Dream

Every `periodDays` a model reads the raw records of the time since the last dream and reports what is worth fixing (`src/core/extensions/dream/`, `src/core/domain/dream.ts`, wired by `src/dream.ts`; card `dream-report`, goal set by the human on 2026-11-18). The reflection acts only on the five kinds of signal code records, and in its first 27 days on prod saw one; the backtest (card `dream-backtest`) showed that `claude-opus-5-5` reading a week of raw records found three and a half of four known problems for about 0.5 USD, where `claude-haiku-5-5`, prod's root model, found none. It is off unless `dream` is set (see "Configuration").

- **A background task like the digest and the reflection.** Its checkpoint holds the window's start (`since`), the next time (`next`) and the last root entry the previous dream covered (`after`). The first dream is due when the task is created and covers the `periodDays` before it; each later one is due `periodDays` after the last and covers the time since it. When the time comes, one commit pins the window's end (`until`, the time the tick runs, so after downtime one dream covers the gap), the last root entry it covers (`upto`), and makes the conversation the dream model answers in. A task a db holds while `dream` is off stays pending, its definition missing, and resumes when it is turned on.
- **The model call is not a round of the root.** It runs in a conversation of its own, owned by the dream task and configured with the dream model, `thinkingLevel: "high"`, no extension and no tool: the request carries no section of the root's prompt and nothing of its transcript, and the dream itself does not wake the root's model. It goes through the root's `models`, so the same provider and key. Chosen over a direct pi-ai call because pi-durable then stores the input, the answer and its usage durably: the submission's `requestId` is `dream:<until>`, so a crash during the call reruns the tick, which finds its submission and waits for it (pi-durable counts the cut-off request as a failed attempt under `settings.retry`, and with no retry left settles it `interrupted`), and a crash after the answer was stored finds it answered and asks no model again. The cost is in that conversation's `pi.assistant` entry, which `inspect`'s `usage` lists like every conversation's, under the dream conversation's id. One conversation per dream, so no earlier dream's input is paid for again.
- **The input is built by code from storage**, never from a model's context (`renderDreamInput`): the root's entries in (`after`, `upto`], the first dream's from its `since`, one line each with `entry:<id>` and the local time where the entry has one: the human's inputs with their interface, the model's text and tool calls cut short with the round's context size, cache read, cost and stop reason, tool results cut short and marked when an error, notices cut short, tool list changes, compactions. An input of a round in `soma.stops` is marked as the human's own stop, and an answer of that round cut off `aborted` as the human stopping it: the backtest rendered the bare `aborted`, and both its models took it for a fault. Then usage per local day (rounds, cost, rounds with no cache read and their cost, largest context), the fact layer's signals (per kind, and those of the window with their evidence ids) and long-term memory (its lines and how many revisions).
- **The log.** With `dream.log` set, the input profiles the log's lines whose timestamp falls in the window: ids, uuids and numbers of four or more digits erased, counted, most frequent first, at most 60 patterns (`LOG_PATTERNS`), with the number of `[soma] started` lines in the window. Lines with no timestamp are one figure and are not profiled. The line format is the one `log-timestamps` pins (`new Date().toISOString()`, one space, the rest); a log the file cannot be read from says why. Without `dream.log` the section says no log was read.
- **Redaction**, before the input leaves the process (`redact`): provider keys, Telegram bot tokens (also inside an API URL, `/bot<id>:<secret>/`), any token of 40 or more characters, tailnet host names and email addresses. Each text is redacted before it is cut, so a cut cannot leave a long token's first 39 characters, and each log line before its ids are erased, so erasing a key's segments that hold a digit cannot leave the rest unmatched; the whole input is redacted once more. Observed text that names the fence is taken out until none is left, so nested markers cannot rebuild one that ends the fence early.
- **The prompt** is the backtest's, in Traditional Chinese like the reflection's, answering in the configured `language`, with the observed records fenced as data (`FENCE_OPEN`, `FENCE_CLOSE`).
- **Output.** The answer goes to the human as one `notice` of class `ambient` on the root, starting with the window, in the same commit as the next checkpoint, so a crash never gives two notices for one window nor loses one. Nothing of the dream's input enters the root's context, and the dream itself does not wake the root's model: a notice has no model message. The report is still an ordinary ambient notice, decided by the human after the milestone's review: where an interface's push policy holds ambient notices (the `summary` preset), the summary of the held notices is a root round, so the root's model reads the report there with the others. When the call fails (the model unknown, the provider refusing, the context too large) or the model answers nothing, the notice says so with pi-durable's reason or that the answer was empty, and the window is not asked about again: the next dream, a period later, covers the time after it.
- **Stubs of this milestone**: the dream acts on nothing (no memory revision, no card, no tool for its model); its findings are not deduplicated against earlier dreams or cards; the report has no delivery of its own, so it is held and summarised like any ambient notice. Acting follows the 2026-10-18 decision when it comes: the behavior layer directly, code through a card and a dispatch, no merge.
- **Known limit**: pi-durable's compaction settings are shared, and `rootCompaction`'s override is keyed by model. When the dream model is the root's, an input past `compactAt` can start a compaction in the dream's conversation, and one past `compactAt` plus 32768 tokens waits for it. With the default, `claude-opus-5-5` for the dream and prod's root on `claude-haiku-5-5`, it does not apply.

### Tickets the human asks for

Decided by the human on 2026-11-07 (card `soma-cannot-open-requested-ticket`). soma is a high-level orchestrator: for a ticket the human asks for, it dispatches an agent with the request as its brief, and that agent writes the card. soma writes no card itself and never asks the human for evidence ids or a format. Before this, `open_card` was the only card tool soma's model saw in a normal turn (the reflection extension's tools are on the root conversation), and its refusal of anything without evidence ids made soma ask the human for them.

- **`dispatch` takes an optional `ticket`**, the human's request word for word; one that is empty or only whitespace is refused by its schema (pattern `\S`, which an invisible non-space character such as U+200B still passes). With it, no card is read; `card` names the job (such as `ticket-<topic>`), which is also the agent's name and its `fleet/<card>` worktree, as for any job. The launch prompt is `composeTicketPrompt` in `src/core/domain/launch-prompt.ts`: the usual unattended rules, then the brief: write one obw task card with the obw pm skill under `pm/<project>/tasks/` of the vault and project the repo's `.obsidian.yaml` names, quote the request word for word as the card's source, change no code, commit and dispatch nothing, and put `卡片：<card>` on the final reply's second line. The rest is the usual job: `startJob`'s rerun checks, the bridge sending the brief at the first idle, the transcript read at the end. A job name the dispatch list already holds for another request, or for a card where this is a ticket or the other way round, starts nothing: `startJob` throws `JobNameTaken`, and `dispatch` returns `dispatched: false` with a reason that fits the clash: a ticket is to be sent again under a new job name, such as `ticket-<topic>`; a card, whose job is named after its file, cannot take another name, so the model is told to dispatch a card only under its own name and to tell the human when a ticket job holds it. The same call rerun after a crash has the same request, so it gets its first job back and starts nothing again.
- **The job stores the request** (`Job.ticket`), and its `完成` goes to the human at once whatever the time since the request (`urgent` in `src/core/domain/report.ts`), as the agent's reply verbatim, so the notice names the card. `需要你` and `失敗` go at once as for any job. An interface at `summary` still holds that notice, as it holds every class: a ticket is no reason to break the do-not-disturb. Instead, when the summary is written, code appends each `卡片：` line of the pushes it covers that the model's text does not carry, word for word (`withCardLines` in `src/core/domain/report.ts`, called by `summaries` in `src/core/hold.ts`); one the model kept is not repeated.
- **Blocked on a permission prompt**, a ticket job wakes the model with a message that says it is a ticket job, whose agent only writes one card in the vault, and tells the model to refuse an Edit or Write outside the vault, or a command that changes code, commits or dispatches (`wakeContent` in `src/core/extensions/dispatch/bridge.ts`). claude takes a refusal as the user interrupting: its turn ends with no reply and no result line, and it waits for a prompt (tried on 2026-11-08 with claude 2.1.319), so the message also tells the model to follow the refusal with `reply`, saying to write only the card in the vault and to finish with the result line. Nothing in code refuses for the model: whether a prompt is refused is its choice, and the brief's no-code rule is otherwise only prose to the agent.
- **The repo** is the one the request is about. soma asks the human which only when no repo it knows fits; the agent finds the vault and project from the worktree's copied `.obsidian.yaml`.
- Not covered by a test: whether a live model picks `dispatch` with `ticket` for a plain-words request. The tool descriptions are what steers it; `test/ticket.test.ts` checks that both descriptions reach the model and that the scripted call writes no card and reads none.

## The two contracts

### Human side (adapter → core)

- **Submit**: `submit({ type: "input", content, entry: { kind: "<source>", data }, requestId })`. The `requestId` is the platform's message id, so a resend is handled only once. The terminal has no message id and uses `terminal:<millisecond timestamp>`: `requestId` is deduplicated across the whole conversation, and counting from 1 again after a restart would swallow new input as resends.
- **Subscribe**: in-process adapters subscribe through the HumanPort in `src/core/human-port.ts`, which turns the stored commits of the root conversation (`Harness.observeCommits()`: its entries, its submissions and its `pi.live` document) and the dispatch list's `watchDoc()` into soma's event types. A `watchDoc()` on `pi.live` gives the `partial` event (see "Answer streaming" below). Dispatch status comes from the dispatch list, so whatever anyone writes into the list, the adapters can see. Out-of-process clients connect through the client socket instead.
- **Notify**: when the core needs to reach the human on its own (stuck, or a report is written), it writes a record with `kind: "notice"`, whose `data.kind` is `question` (stuck, needs the human to answer) or `report` (a report is written), and whose `data.class` is the push's class (see "Whom to push to when there are several interfaces"). The core decides what each adapter does with it, from the interfaces' policies and the push target, and the adapter applies that. The answer of a turn started by a `requestId` beginning with `schedule:` (`PUSHED_ANSWERS` in `src/ports/human.ts`) is also pushed to the human as a notice; since 2026-11-05 the core marks it with its class and delivery, and the adapters no longer pick it out by prefix. The `digest:` turn is not pushed, because the digest task writes its answer as a `notice` record with `data.kind: "report"`, and pushing it again would duplicate it.
- **Answer a prompt**: for a prompt the model hands to the human with `escalate`, if the agent side can read its options and fingerprint, the `question` notice carries `data.choices` (card, fingerprint, options), and the adapter can let the human pick directly. After the human picks, the adapter calls HumanPort's `respond(card, { option, fingerprint })`, and the core calls AgentPort's `respond` directly without running the model (see "Two kinds of interaction must not mix"), then records an `answered` entry in the dispatch list. When the fingerprint does not match, no keys are sent, and the adapter passes the returned refusal reason to the human. Telegram draws each option as an inline button whose `callback_data` is `<option>:<fingerprint>:<card>`. Over 64 bytes it sends text only, because a truncated card name would answer a different job.
- **Ask with options (2026-11-17, as built; card `soma-ask-buttons`)**: soma's own model asks the human a question with a small closed set of answers through the `ask` tool (`src/core/extensions/ask/index.ts`), not as plain text the human must type an answer to. The tool takes the question and 2 to 4 options, each non-empty, distinct and at most 40 characters; anything else is refused as an error result the model reads, and nothing is asked. Its description says when to use it (yes or no, now or later, which of a few named things), not for an open question, and that the question is sent to the human as its own message, options included, so the model ends its turn with no text unless the human needs something else besides the question, and never restates the question or its options; its result (`{ asked: true, note }`) says the same in `note`. The guidance is in the description and the result only, not in a system prompt section. The description names no interface: the human answers with one press where their interface shows buttons, or types the answer; each interface says what it shows in its `ABILITIES` text (see "The model is told what the interface can show"). In one commit it records the question in the `soma.ask.questions` doc and appends a `question` notice of class `action` whose `data.choices` is the second form of `Choices` (`SaidChoices` in `src/ports/human.ts`): `{ question, options }`, naming no card, the options numbered from `1`. A question asked in a round no interface started (schedule, a job's report, digest, a foreign agent, a summary) is treated by the push policies, the push target, escalation and holding as an escalated prompt is. A question asked in a round an interface's input started is part of soma's reply to that input instead (2026-11-17, card `ask-in-reply`; under Telegram at `summary` the human asked for options in the chat and got no buttons, since the question was held for the summary): the tool looks up the entry kinds of the running round's inputs as the `interface` section does (`inputKinds` in `src/core/extensions/interfaces/index.ts`), keeps those that are an interface's (`AskOptions.interfaces`, the kinds `src/main.ts` has abilities texts for), and the notice names them in `data.replyTo`, each one when a steered round mixes them. The HumanPort delivers it to each of them at once, whatever its policy, `hold` and `log` included, the round's first such question ringing and any later one in the same round `quiet` (see "A question is the whole reply" under "Whom to push to"), and holds it for none of them, so no summary counts it or offers it there again; every other interface gets the delivery its own policy gives an `action`, holding and escalation included, as before (see "Whom to push to"). The question id is the first 16 hex digits of the SHA-256 of the tool call's id, so the tool is `replay: "safe"`: a rerun finds the question and appends nothing. A press goes through `HumanPort.say(question, option, { entry, requestId })`, not `respond`: in one commit the core checks the doc, marks the question said, and submits the option's label to the root conversation as the human's input (`whenBusy: "followUp"`), with the entry kind and requestId of the interface it was pressed on, so it starts a round like a typed message and its answer goes back to that interface; no agent is involved, and a press counts as input for presence as `submit` does. A press on a question already said, from any interface, admits nothing and returns `settled` with the label said then; an unknown question or option is refused too; the doc is read by its own keys only, so an id such as `__proto__` or `toString` is an unknown question. A settled press emits a `said` event (`{ question, label }`) to every subscriber. A question said is a prompt gone (`promptGone` in `src/core/domain/push.ts`), so it is not escalated, and a summary leaves it out and does not offer it again, even when it was pressed while the summary's round ran. When the human types an answer instead of pressing, nothing special happens: the buttons stay until pressed.
  - **Telegram** draws each option as an inline button whose `callback_data` is `ask/<question>/<option>`, which holds no `:` and so never reads as a prompt's `<option>:<fingerprint>:<card>`. A press calls `say` under the requestId `telegram:ask/<question>`, one per question, with entry data `{ pressed: <message id> }`; the pressed message's keyboard becomes one disabled button `已選：<label>` (`editMessageReplyMarkup`), and the round shows the Thinking draft under the prompt's message id; it gets no reactions, since there is no message of the human's to mark. A second press on that message is only answered (`answerCallbackQuery`) and changes nothing; one the core finds settled, as after a restart, shows `已選：<label said>`, and an unknown question or option `未送出：<reason>`. A `said` event, from any interface, turns every other message here offering that question into the same disabled button. A press whose `say` or `respond` throws is reported (`onError`) and its update is confirmed like any other, so it never holds back the polling (before, the throw went to the poll loop and the update was retried with every update after it waiting). A question's press whose `say` throws is answered `未送出：出錯了，可以再按一次` and its message is not settled, so the human can press again; `say` is idempotent through the questions doc. An escalated prompt's press whose `respond` throws keeps its message settled, as before the ask work, and shows `不確定有沒有送出：出錯了，請到 agent 的畫面確認` as the answer and as the one disabled button: `answerJob` can throw after the keys went (a failed decision commit, a rex `press` whose reply is lost), and on rex, herdr and tty the fingerprint is the prompt's content, so a second press could answer a later identical prompt. While a press is in flight, a `said` or `job` event leaves its message to the press and records its own text; a `say` that then throws shows that text and leaves the message settled. As for prompts, the messages showing a question are kept in memory, so after a restart a question shown before cannot be settled by an event; a press on it still is, by the core's refusal.
  - **The web page** gets the options on the `notice` message (`choices`), and the bubble shows one button per option under the words (`src/adapters/web/page/choices.js`). A press sends `{ type: "say", id, question, option }` with a fresh id, resent on reconnect as typed words are, and the fox listens until the round starts; the server calls `say` under `web:<id>` and answers `accepted`, or `said` with the id when the question was already said, or a failure. Every page gets `said` messages, and a box settled shows one disabled `已選：<label>` button. A bubble whose options wait for a press does not fade on its own; a tap outside the buttons still lets it go. A prompt's options (`Choices` with a card) are still not offered on the page.
  - **The terminal** prints the options as a numbered list under the question (`  1. 好`), and the human types the answer as any line.
  - **Where it sits.** `askExtension()` comes after the MCP extensions in `src/main.ts` and before `interfaces`. pi-durable offers the tools in extension order, and its planner (`planTools` in `harness/prompt.js`) removes and re-adds every tool when a new one appears in the middle, so placed after `dispatch`, as at first, the first request after the release that adds it would have re-added every tool. Last among the tools, it is appended alone (checked by planning a transcript whose tools are the old list against the new one, 2026-11-17).
  - The escalated-prompt path (`Choices` with a card, `HumanPort.respond`, its buttons and `已在別處處理`) did not change. Checked with unit tests and the fake Bot API (`test/ask.test.ts`, `test/adapters/telegram/telegram.test.ts`, `test/adapters/web/`, `test/adapters/terminal/terminal.test.ts`, `test/hold.test.ts`); not checked: the page's bubble wiring in a browser (only `choices.js` is tested, under linkedom), and a live model choosing `ask`.
- **Options a job's agent lists (2026-11-17, as built; card `agent-question-buttons`)**: a dispatched agent still may not use AskUserQuestion, but the first launch rule (`src/core/domain/launch-prompt.ts`) now gives it one fixed way to offer the human 2 to 4 short options at the end of a `需要你` reply: a line `選項：`, then one line per option numbered from 1 (`1. A`, `2. B`), at most 40 characters each, and nothing after them. It reads as plain text where no buttons are shown. `listedOptions` (`src/core/domain/options.ts`) reads the last `選項：` line (an ASCII colon is taken too) and the lines after it, blank lines aside; every one must be numbered in order from 1. Agents dress the form in markdown, so since the review of 2026-11-17 the header may also be bold or a heading (`**選項：**`, `### 選項：`), and a number bold, full-width, or followed by `)`, `）` or `、` with or without a space (`**1.**`, `１.`, `1)`, `1）A`, `1、`); a `.` or `．` needs a space after it (second review, 2026-11-17), so `1.2.0 升級` is no option numbered 1 with the label `2.0 升級`; bold markers are taken off only where one pair wraps the whole line, the number or the whole label (`**1. A**`, `**1.** A`, `1. **A**`), and any others stay in the label (`用 **kwargs`, `**A** 或 **B**`). The launch rule still names only the plain form. The labels must pass the same rules as `ask`'s (`optionsRefusal`, moved there from the ask extension: 2 to 4, non-empty, distinct, at most 40 characters). Anything else lists no options, and the reply is told as before.
  - **The notice.** When the event bridge (`src/core/extensions/dispatch/bridge.ts`) tells a `需要你` turn at once and its reply lists options, the same commit records the question in the `soma.ask.questions` doc (`askForJob` in `src/core/extensions/ask/index.ts`) with the job's turn (`JobQuestion` in `src/core/domain/dispatch.ts`: its card, the reply's record id, and when it was told), and the `question` notice of class `action` carries `SaidChoices` with `job` set to the job's card. The notice's text is the reply without the options list, which every interface shows from the choices instead; the list is also out of the 600 characters `clip` keeps. The question id is the first 16 hex digits of the SHA-256 of `job`, the card and the record id, so the same turn asks once. Being `SaidChoices`, the notice uses everything `ask` built: Telegram's `ask/<question>/<option>` buttons, the page's buttons, the terminal's numbered list, the `said` event that settles every interface's buttons on one disabled `已選：<label>`, and `promptGone`, by which a question said is neither escalated nor offered again after a summary. It names no interface in `replyTo` (no input of the human's started the bridge's commit), so the push policies treat it as any `需要你` notice: under `summary` it is held and offered again with its buttons after the summary. A `需要你` reply without options, the `ask` tool and escalated prompts (`Choices` with a card) are unchanged.
  - **A press.** It goes through `HumanPort.say`, as a press on an `ask` question does; adapters need not tell the two apart before the press. On a question naming a job, `say` reads the job in the commit that would settle the question and settles it only if the job still waits on it (`awaitsAnswer`): the job's last recorded turn is the one that asked, the agent is `idle` or `done`, no deferral holds its stop or prompt (`reclaim` absent or `failed`), and no decision other than an escalation was recorded since the question was told, so a `reply`, or an earlier press, stops it waiting. Otherwise nothing is sent and the press returns `not_waiting`. Settled, the label is sent to the job's agent as its next prompt with `AgentPort.prompt`, as the `reply` tool does, with no model round and no input to the root conversation; the job then records a `replied` decision with the label and the reason `HUMAN_CHOSEN`, so the turn that answers it is told at once even when it is `完成` (`urgent`), and `said` is emitted. The result is `{ said: true, label, job }`. A prompt the agent side refuses before typing (`PromptRefused`) leaves the question unsettled. Since 2026-11-17 (review of `agent-question-buttons`) the refusal says whether the agent was busy (`PromptRefused.busy`, set by rex for a claude `working` or `blocked` and by ACP for an agent in a turn): a busy one means the job no longer waits, and the press returns `not_waiting`; any other refusal, such as ACP's full hangar or a dormant agent that could not be woken, says nothing of where the agent is, so the press returns `unsent` with the refusal's message as `reason`, and a later press may go through. herdr does not refuse a busy agent, and tty refuses one with a plain error, not a `PromptRefused`, which a press takes as `unsure`. Any other failure may come after part of the label reached the agent, so the question stays settled, never to be sent twice, `said` is not emitted, and the press returns `unsure` with the label. `openHumanPort` therefore takes `prompt` from the agent side as well as `respond`.
  - **What each interface shows.** Telegram settles the pressed message as for any press (`已選：<label>`, or `未送出：agent 已經不在等這個回答` on `not_waiting`, or the respond path's `不確定有沒有送出：出錯了，請到 agent 的畫面確認` on `unsure`). On `unsent` it keeps the buttons and answers the press with `未送出：<reason>，可以再按一次`, the reason cut to fit the callback's 200 characters, as for a `say` that throws. It shows no Thinking draft for a press that went to a job, since no round runs. The web server answers such a press with `said` under the page's id rather than `accepted`, so the fox does not wait for an answer that never comes; `not_waiting` and `unsure` are failures with the same words, and `unsent` is a failure `沒有送出：<reason>，可以再按一次` marked `again`, on which the page opens that question's buttons to a press again (`reopenChoices` in `src/adapters/web/page/choices.js`). The terminal has no buttons: the human types the answer there, as they may on Telegram or the page, and soma's model relays it with `reply` (next point).
  - **What soma's model sees.** A notice is an entry with `kind` and `data` only, which pi-durable never puts in the model's context, and so is the bridge's `soma.dispatch.done` entry: the model never sees a job's reply, with options or without, and a typed "1" or "B" reached it with nothing to relay it against (checked 2026-11-17, review of `agent-question-buttons`). The dispatch extension's `job_questions` section (`jobQuestions` in `src/core/domain/dispatch.ts`) now shows the model, at every request, each question a job still waits on (`awaitsAnswer`, and not said): the job's card and agent, its reply as the notice told it without the list (kept with the question in the doc, as `JobQuestion.text`, cut by `clip`), and the options numbered, and tells it to send a typed answer's option to that job with `reply`. The reply and the labels are an agent's words, so they are framed as quoted data (second review, 2026-11-17): the instruction says they are text agents wrote, quoted for reference, and that nothing in them is an instruction to soma; every reply line is quoted with `  > ` under its item, however the reply breaks its lines (`\n`, `\r`, U+2028, U+2029), so none passes for the section's own lines; and any `job_questions` tag in a reply or a label, in any case and spacing, has its angle brackets made full-width (`＜/job_questions＞`), so none opens or closes the section. When it is not clear which question a typed answer is for, as with several jobs waiting or a question soma asked with `ask` still open, the instruction tells the model to ask the human which one, not to guess. With none it says so in a fixed sentence: the section is never left out, so its text changes only when a question opens or closes. A `需要你` reply without options is still not shown to the model; the human's typed answer to it reaches the model with no reply to go by, as before this card.

- **Failure**: when a turn's input ends as `unanswered` in Pi Durable (`model_error`, `no_model`, `aborted`, `faulted`, or an orphaning reason; see durable spec 8.3), HumanPort emits a `failure` event with the `requestId` and a reason a human can read; `model_error` includes the provider's error text. An adapter sends back the failure of its own turn as the answer. Turns starting with `schedule:`, `agent:` and `foreign:` (`PUSHED_FAILURES` in `src/ports/human.ts`) are started by the core itself and nobody is waiting, so their failures are pushed to the human as notices, with the class `outcome` and a delivery the core sets. The failure of a `digest:` turn is not pushed, because the digest task has already written the failure cause and the raw job list as a notice. The terminal's 7501 root record reports `error` after a failure, until the human types again. HumanPort sees only commits stored after it attached, so a failure already emitted is not emitted again after a restart. An abort the human asked for with `HumanPort.stop` is not a failure: it is told as `stopped` (see "Answer stop" below).
- **Progress**: when a tool result's `details` carries `forwarded: true` (`FORWARDED` in `src/core/notice.ts`; only `reply` for now), HumanPort emits one `notice` for each input already admitted to the turn, with `kind` `forwarded`, carrying the `requestId` and no content. It is only an event and is not written as a record, because progress does not need to survive a restart: an input admitted before a restart gets no submission event again, and its `forwarded` is lost. On 2026-10-23 it was decided to put it in `notice` for now and judge later whether to split it into its own event. Telegram marks progress on the human's message with `setMessageReaction`: 👀 when received, 👌 for `forwarded`, 👍 for the answer, 👎 for a failure, 🫡 for a round the human stopped. A non-premium bot can have only one reaction per message, so each one replaces the one before; the table is `REACTIONS` in `src/adapters/telegram/index.ts`. A failed reaction is only logged and does not block polling.
- **Thinking draft**: once the core has admitted a message (`human.submit` resolved), Telegram also shows the "Thinking…" placeholder in the chat: `sendMessageDraft` with an empty `text` and the message's id as `draft_id` (non-zero, as the Bot API requires). A draft is a 30-second preview, so it is sent again every 20 s (`draftRefreshMs`) until the answer or failure of that `requestId` arrives; the message that answers it makes it go. Nothing is sent once `signal` aborts. A refused draft is reported through `onError` like a reaction and stops neither polling, sending nor the reactions. A round's draft is sent again for at most 10 minutes after its first send (`draftLimitMs`); past that the refresh stops, and the answer or failure still arrives as usual. So a round whose answer or failure never reaches the adapter, such as a message Telegram delivers again after a restart, which the core admits again silently, does not keep "Thinking…" coming back. The open drafts live in memory only: a round admitted before a restart shows none. Once the answer's text streams, the draft shows it instead of the placeholder (next point). Every draft carries the Stop button (`can_stop`; see "Answer stop" below).
- **Answer streaming (2026-11-17, as built; card `answer-streaming`, decided by the human that day: Telegram only, the stop button later)**: the text of an answer reaches Telegram while the model writes it.
  - **The core.** pi-durable commits a throttled copy of the response being written into the root conversation's `pi.live` document, `generation.message`, at most every 100 ms, as a deferred commit: a watch sees it at once, `observeCommits()` only once storage gets it, up to a second later. So `openHumanPort` (`src/core/human-port.ts`) watches `pi.live` with `watchDoc()` beside its commit observer and emits a `partial` event (`SomaEvent` in `src/ports/human.ts`): the requestIds of the inputs placed in the running round and the whole text so far of the current generation (its text blocks joined, thinking and tool calls left out), never a delta. It is emitted only when that text changed for the round, so a commit that only grows the thinking emits nothing. Each partial is handled behind the commits already observed, on the same queue: the inputs are known as placed by then, and once the round's answer or failure has been handled its inputs are no longer placed, so a partial that comes after it says nothing. Text written before a tool call streams too; when the tool-calling answer ends that generation, or a retry replaces it, the text starts over from empty and the empty text is emitted. The event is not stored and not replayed: a subscriber that attaches mid-round gets the next one, and after a restart a round that was already running streams nothing, since its inputs were placed before the HumanPort attached. The round still ends with `answer` or `failure`, the only durable outcome, and the event names no interface.
  - **Telegram** (`src/adapters/telegram/index.ts`). A partial for a round from this chat, one with a draft open, becomes that round's draft under the same `draft_id` as the placeholder: `sendRichMessageDraft` with `rich_message: { markdown }`, the form the final `sendRichMessage` takes, so the draft is in the answer's formatting; a text that is empty after trimming sends the placeholder with `sendMessageDraft` as before. A partial of any other round is ignored. Draft calls of a round are at least `draftIntervalMs` (1 s) apart, counted from when the last one went, and only one is in flight at a time: a text that comes sooner, or while a call is in flight, waits, and only the newest text goes once the time has come and that call has ended. So the texts in between are dropped, the last is not lost, and an older text never reaches Telegram after a newer one however slow the network. The 20-second refresh and the 10-minute limit stay, and a refresh sends what the draft shows, the newest text or the placeholder, under the same rules. A draft is best effort: draft calls are never on the `sending` queue, so none delays, reorders or fails a message, and the final answer waits for no draft call. A text draft refused with anything but a 429 is skipped, since a draft may hold half-written markdown (an open fence, a table in progress) that Telegram might refuse while the next text is fine: the draft keeps what the last draft taken showed and the next text goes. The round's first such refusal is reported through `onError` and the later ones are not; after three in a row (`DRAFT_REFUSALS`) text drafts stop for the round, whose refresh then sends the placeholder; a draft taken, the placeholder included, starts the count over. A refusal carrying `retry_after` (flood control) is reported, and every draft of the chat waits that long, at most 60 s (`FLOOD_WAIT_MS`), after which the newest text goes; a longer `retry_after` also stops the round's text drafts (a timer that long would overflow and fire at once). A text longer than one rich message (32768 bytes of UTF-8, the measure the answer uses) is not sent and the draft keeps the last text that fit; a shorter one, as after a tool call, is shown again. Once the round's answer or failure is handled its draft is closed: a text still waiting is dropped, and a draft call in flight is aborted through its own `AbortSignal` and its outcome, a refusal included, ignored. The final answer is sent exactly as before, whatever was streamed. The adapter takes `now` and `setTimer` for the clock its drafts, and a message's wait for flood control, are timed by.
  - **Flood control on messages.** Drafts share the chat with the answer, and a 429 on `sendRichMessage` used to fall to the HTML path, which flood control refused too, so the answer was lost. Every call of the `sending` queue (answers, failures, notices and prompts with buttons: `sendRichMessage`, and the HTML path's `sendMessage` with its plain-text resend) refused with a 429 carrying `retry_after` is reported, waits that long and goes again, at most twice (`SEND_RETRIES`) and waiting at most 60 s in all (`FLOOD_WAIT_MS`), each call counted alone. A wait past either is not taken, and the refusal then goes the way of any other: a `sendRichMessage` falls to the HTML path, and a refused part is reported and ends its message. The wait is inside the queue's step, so the messages behind it wait their turn and the order holds; it ends early once `signal` aborts. Edits of buttons, reactions and drafts are not on this path.
  - **The web page and the terminal** ignore the event and show whole answers, as before.

In one commit it reads the input's submission (`submissionByRequest`) and `pi.live.run`, and records the stop: it takes only when the input is among the run's `inputs`, so a queued or settled input, an unknown requestId, a run that answered and runs only its `afterRun` tasks (whose `inputs` are empty), and a second ask for a round already being stopped stop nothing and return false; a later round is never stopped. The HumanPort then aborts the round with `harness.abortTask(run.taskId)` as soon as none of its tool calls runs (`pi.live.tools` absent): at once while the model writes, so the model request is cancelled through the task's signal, pi-durable appends the committed partial as an assistant entry with `stopReason: "aborted"`, which the model's context leaves out, and settles the run's inputs `unanswered` with reason `aborted`. While a tool round is on, aborting the run would abort its running tool tasks first (abort runs bottom up), so the `watchDoc()` on `pi.live` waits for the commit that ends the round's tools, records their results and hands the run to its next generation (`run.taskId` changes, `tools` goes), and aborts that generation before it asks the model. A call not started yet when the stop was taken, such as the next call of a sequential round, is blocked too. A nested call, one a running tool makes through `executeTool`, is that tool's work and goes on: the stop lets a running tool finish. The guard is a hook only, with no tool or section, so it changes no request.

An abort the human did not ask for, and any other end of a round a stop was asked for, is told as before. No `partial` of a stopped round is emitted after the stop, not even one the watch saw before it and the queue handles after it. A stop older than the 200 kept is listed there as an `aborted` failure again.

So once a stopped round's settlements are handled, the HumanPort submits a `continue` in a commit that finds no run and an input (`steer` or `followUp`) in `pi.inbox`. The continue places the oldest queued follow-up, which runs as the next round with no further input, whoever queued it (schedule, agent, foreign, the human's follow-ups); the follow-ups after it run one round each, as after any answer. A continue is never sent with no input queued, since it would answer the stopped input. The next round's context holds the stopped input without the partial answer, so it reads as two user messages in a row. A continue's run takes its `first` entry from the stopped run, so the replies counted for a notice's ring (`rang`) start past `after`, the stopped round's last entry: the next round's first question to an interface rings there, whatever the stopped round asked. The `asked` lookup of an answer starts at its round's own inputs, so it never counted the stopped round.

One from another chat is ignored. - **Telegram shows the model's markdown as a rich message, and as HTML when it cannot (2026-11-17, as built).** Every text the adapter sends, whether answer, notice, pushed failure or prompt with buttons, goes as one `sendRichMessage` call (Bot API 10.1) with `rich_message: { markdown }` holding the text as the core gave it, and the same `reply_markup` and `disable_notification` it would have had; an empty text is still `（這一輪沒有文字回答）`. Where the client socket stands:

- **Pi Durable has no server, transport layer or RPC.** There is no server code anywhere in `durable/src`; the spec says only "Transport backpressure and disconnect policy belong to the consumer" (spec:4773).
- **Chord has related building blocks.** The server side, `acceptWebSockets` (`chord/src/websocket.ts:18`), needs its own ws server and a principal validator (`websocket.ts:5, 14`); the client side, `webSocketLink`, is at `chord/src/link.ts:414`, and state changes are applied with `@earendil-works/chord/delta`.
- **Sending messages remotely must be written ourselves.** It needs a method that wraps `Conversation.submit`.

### Agent side (core → agent adapter)

Every agent adapter implements the same set of actions:

| Action | herdr implementation (all sources are cc-mobile commit d9f0690) |
|---|---|
| Start | `workspace.create` → wait for the shell to be ready → `agent.start{name,kind,pane_id,args}`, with `--session-id` in args → poll `agent.get` until `interactive_ready` (`server/herdr/registry.ts:140-215`) |
| Send a prompt | Check the status is idle or done and the input box is empty (`send-routing.ts:62`) → `pane.send_text` → `pane.send_keys Enter` → an optional start check that presses Enter again if nothing moved (`server/herdr/send-routing.ts:207-266`; only `/api/launch` turns this option on) |
| Status events | The native statuses are idle, working, blocked, done and unknown; the first four map to idle, running and requires_action, and unknown is dropped (`server/herdr/agent-state.ts:20-30`). Inside soma the OSC 7501 vocabulary is used instead; see the next section |
| Read the result | Read the transcript (see the previous section) |
| Respond to a block | `pane.read source:detection` parses the prompt (`native-permission.ts:172`) → compare the fingerprint → read the screen again and compare before sending → `pane.send_keys` (`server/herdr/permission/native-permission.ts:334-440`). On blocked, soma reads the screen to fill in `kind` and the fingerprint; the fingerprint goes to the model with the input that wakes it, and the model brings it back with its answer for comparison |
| Stop | `workspace.close` (`server/herdr/backend.ts:477`, `registry.ts:252`). soma's herdr adapter does not implement it yet (`src/adapters/herdr/agent-port.ts:185`) |

soma and cc-mobile both dispatch work into the same herdr hangar session. The hangar name comes from an environment variable in `ecosystem.config.cjs:48`, currently `fleet`; the code has no default (`server/config.ts:131-138`). The concurrency cap is the number of performance cores minus 2, at least 1, defaulting to 4 when the core count cannot be read, and can be overridden with `CC_MOBILE_HANGAR_CAP` (`server/hangar-cap.ts:1, 52`). cc-mobile takes its occupancy from the number of agents actually running in the hangar (`server/sided-backend.ts:168-171`), so it also counts agents soma dispatches straight into the hangar. The other way round, if soma dispatches on its own, it must use the same formula.

herdr's connection is not JSON-RPC 2.0. Each call opens a new unix socket connection and sends `{id,method,params}` plus a newline. The protocol version pinned now is 22 (`server/herdr/transport.ts`, `client.ts:64`; `src/protocol/wire.rs:20` in herdr 0.9.5 is also 22).

### The rex implementation (tested 2026-10-24)

rex is a terminal multiplexer and also the terminal itself. The versions checked were rex `0.0.1792787366-g623b2d` (API revision 7) and Claude Code 2.1.310. The API docs are at the server's `GET /llms.txt`, and each method's JSON Schema is at `GET /api/help`. On 2026-10-24 an independent review rechecked this section; points marked "not re-verified" were tested only once, and the review did not rerun them.

rex lacks four things herdr handles for soma: a transition counter (`state_change_seq`), refusing a duplicate name (`agent_name_taken`), creating worktrees, and reporting the trust dialog as `blocked`. The rex adapter and the core must make up for them; how is written in the points below.

- **Connection.** The server speaks HTTP on the unix socket `~/Library/Application Support/rex/server.sock`. The control connection is a WebSocket on `GET /api/control` with subprotocol `rex.control.v1`. It first sends `hello` with `api_revision`, then `{type:"request",id,method,payload}`. The server supports revisions 0 to 7 and negotiates downward, unlike herdr, which requires the protocol numbers to be exactly equal.
- **Status.** Claude Code sends OSC 7501 by itself inside rex, so status reporting needs no integration. `rex skill setup` also installs a SessionStart hook in `~/.claude/settings.json`, which only tells the agent which session and block it is in and has nothing to do with status. The block method `program_status` returns records with `state`, `kind`, `msg`, `app=claude-code`, `owner` and `updated_at`. The test saw, in order, `idle`, `working`, `blocked` (`kind=question`, `msg` is `answer: <question> (<option> · <option>)`), `blocked` (`kind=permission`, `msg` is "approve Bash: touch probe.txt"), and `done` (not re-verified).
- **Look only at the root record.** A subagent leaves child records with `id` and `title` in the same block. In the test, when a subagent asked for permission, the root record became `blocked` while the child record stayed `working` (not re-verified), so the agent's status is taken from the record without an `id`.
- **Recognize claude by `argv0`.** The record's `owner.name` and the `process` method's `foreground.name` are both `2.1.310`, because the executable is at `~/.local/share/claude/versions/2.1.310`; only `foreground.argv0` is `claude`. The pid is also taken from `process`, so it can be found even when there is no 7501 record (for example, at the trust dialog).
- **The trust dialog sends no signal.** On 2026-10-24 the first-visit folder-trust dialog was on screen while `records` was empty. herdr reports `blocked` on the same screen and the event bridge wakes the model to answer it (see the point about the first prompt of a dispatch in "Event bridge"); under rex there is no record and no event, so the agent would sit on the dialog and soma would never know. Re-checked on 2026-10-26 with Claude Code 2.1.310 and rex `0.0.1792787366-g623b2d` (API revision 7), each time starting `claude` from an interactive shell in a rex block:
  - `<soma checkout>/.claude/worktrees/<name>`, a linked worktree of a repo the human has trusted: no dialog, and `program_status` already held one root record with `state=idle`. claude wrote no project entry for the worktree path, so the trust it used came from the main checkout.
  - `<fresh repo>/.claude/worktrees/<name>`, a linked worktree of a fresh, untrusted repo under `~/.cache`: dialog shown, `records` empty.
  - A linked worktree of the same fresh repo, placed outside the repo: dialog shown, `records` empty. This matches what herdr's smoke run saw that day in `~/.herdr/worktrees/…`.
  - A fresh `mktemp -d` directory under `$TMPDIR`: no dialog, and claude wrote `hasTrustDialogAccepted: true` for it without asking. That control was invalid, because claude seems to trust `$TMPDIR` on its own. On 2026-11-04 a fresh git repo under `$TMPDIR` did show the dialog, so that trust holds for a plain directory at most, not for a repo.

  So `.claude/worktrees/` does not exempt a folder from the dialog. The worktree inherits trust from its main checkout, and claude asks wherever the repo itself is untrusted. The worktree still goes at `.claude/worktrees/<card>` (see the next point); that is enough for repos the human has already trusted. For any other repo, the adapter must catch the dialog itself: when the foreground is claude and no record has arrived for a few seconds, it reads the screen and, if it finds the trust dialog, emits `blocked:kind=permission`. This check is part of the plan, not an optional backup.

  The rex smokes that assume no dialog (`smoke/rex-dispatch.ts`, `smoke/rex-defer.ts`) therefore default to one fixed repo that the human trusted once, `~/.cache/soma-smoke/repo` (`smoke/smoke-repo.ts`), and refuse to start if it is missing or untrusted. They do not default to the current directory: in a muster worker's directory, a clone and so its own repository root at a new path each run, that would stop at the dialog, and a yes would leave one more entry in `~/.claude.json`.

A `done`, `idle` or `error` reported with no `working` seen since clears it (M5-2d), so "unknown" means unknown and the read does not wait against the turn before's end: a re-stamp of an end, a resync after a reconnect gap that spanned the turn's start, so it reads the new `done` while no `working` was seen, a `working` dropped because its seq is below one already reported, an event skipped because `process` read a transient non-claude foreground, or one whose payload failed its schema. Without an end the transcript is read at once, so a re-stamp reads the last record the core already holds and records nothing, without waiting, whether the turn ended on a reply or on the user. M5-2c kept the end on such reports: a turn that ended on the user waited out the 2 s at every re-stamp and recorded a phantom `未知` turn each time, and a turn read across a gap came back at once as the turn before's reply. One gap case is recovered rather than unknown: a resync that reads a turn's `done` while that turn's `working` event is still queued behind it, which the watch then drops as older than what it reported; that `working`, newer than the report before the `done`, still marks the `done` as the end of a turn (or, when the resync read `working` or `blocked`, the turn as on), and `readResult` takes the end only after the watch's work queued when it asks, which its own calls to rex follow on the client's one connection, so that `working` has been tracked. Work queued after that is not waited for, but the read does wait for the backlog queued before it asks, which a block re-reported faster than its unparsed screen is read three times can grow without bound (a known limit, left open: the M5-3 measurement saw no re-report of a resting `blocked` or `idle` in 60 s each, see "No transition counter" above, so the backlog needs a block re-reported many times a second, which no run has shown); the first M5-2e build waited until the queue was empty, which another block re-reported faster than its screen was read could postpone without end. M5-2d took the end after its first call to rex, which a slow resync of another block could beat, and then read the turn before's reply at once. A resync's report goes through the same rule as an event's and does not clear the end on its own: a `working` seen before a short gap still tells that the `done` the resync reads ends its turn, and discarding it would read that turn at once, before claude wrote it. The loss when the watch cannot tell, and the transcript does not hold the turn yet: the read returns the turn before's last record, which the core takes for a turn already recorded, so the turn is recorded only at a later re-stamp read once claude wrote it, or not until the next turn. At the startup reconcile, which runs before the watch, that is a turn that ended within about 50 ms of a restart. The wait sleeps no longer than is left of the 2 s; before it, the read waits for the watch's work already queued, bounded by that backlog. Both run inside the bridge's queue, which a slow read holds up for every agent; the 2 s bound was accepted.

### Foreign agents

A foreign agent is any pane, in any session of the agent side, whose foreground is claude and which is none of the agents soma dispatched; the human's own coordinating sessions count. The exclusions are made in the rex adapter, not the core. Decided 2026-11-05: a rex session whose label starts with `soma-` holds no foreign agent, which covers prod's `soma-hangar` and every `soma-smoke-*`, so a dev instance, prod and the rex smokes do not treat each other's panes as foreign; every other session still counts. Decided 2026-11-07: the port's own hangar is the exception, since the human opens claudes there too and they were invisible; its panes count unless they are soma's jobs, which the adapter tells by the label `start`, `resume` and a handover's `take` (all through `openWindow`) give each job's block, the claude session id, read from the hangar's `session.list_blocks` so a detached block or one placed after a split counts, so a window the human opens in the hangar, with no such label, is foreign, as is a block they split off a job's window. Until 2026-11-05 soma saw only its own jobs, and the event bridge ignored every agent it did not dispatch ("Resident service"), so asked "目前有哪些正在運作的 session" soma said none while the human had claude running in other rex sessions. Its environment is soma's less a parent claude session's marks (`agentEnv` in `src/agent-cli/env.ts`, shared with tty), plus `SOMA_AGENT=<card>` and, as rex gets them, `SOMA_SOCKET`, `SOMA_NODE` and soma's `bin` first on `PATH`; the adapter hands its environment to the Claude CLI it runs, so `soma defer` works in the agent's Bash. `start` returns once `initialize` is answered (within 30 s, else it kills the process and throws with the last stderr line); `session/new` follows in the background, with the cwd and no MCP servers, and its answer is reported as `idle`. That first idle is where the event bridge sends the brief, as for every adapter ("Event bridge"). The core lists the job only once `start` returned, and the bridge drops a status of a job it does not list, so an idle that comes first would hold the brief for good: the adapter resends that same observation, under its seq, every `recheckMs` (10 s) until the agent reports anything else or is stopped. A job listed late takes the brief at a resend; one that took it already reads a resend as the observation it recorded, which does nothing. The client advertises no capability (no fs, terminal or elicitation), so claude uses its own tools and keeps `AskUserQuestion` disabled. claude-agent-acp reads the user, project and local settings, so the permission mode is the user's unless the repo sets one.
- **Session identity.** claude-agent-acp picks the session id itself (`randomUUID` in its `createSession`, which overwrites a client's `_meta.claudeCode.options.sessionId`), so it is not the one the `StartRequest` carries. The job keeps soma's, which `list` reports. The adapter records, by agent name, the card, soma's session id, the ACP session id and the cwd in `<db>.acp-sessions.json` (mode 0600, written whole and renamed into place), which is what `session/load` needs for a restart and for resume. `stop` adds `stopped: true` to the entry before it closes the session and keeps the rest, which a resume needs, and a resume takes the mark off once the session is loaded; an agent stopped while its session opened gets the mark when `session/new` answers. A new `start` of the name writes a fresh entry. Entries are never removed.
- **Status, in the 7501 vocabulary, from the protocol.** `idle` once the session is open, resent as above until the first prompt; `working` when `prompt` sends `session/prompt`; `blocked` with `kind: "permission"` while a `session/request_permission` waits, and `working` again once it is answered; at the prompt's response, `done` for `end_turn`, `done` with `msg` "the turn stopped: <reason>" for `max_tokens`, `max_turn_requests` and `refusal`, and `idle` for `cancelled`, which only a handover's cut asks for; `error` when the process exits on its own, naming its code or signal and its last stderr line. `session/update` notifications are progress only and are not read. A seq is the adapter's clock in microseconds, never repeated, as tty's, since an agent's process lives no longer than soma; an agent woken after a restart reports under the new soma's clock, past every seq the last one used unless the wall clock went back.
- **Permission requests need no screen.** The blocked status carries the request's options numbered from 1, as the wake tells the model to answer, each labelled with the option's `name`; its `msg` is `approve <tool call title>`, then the command, path or description from the tool call's `rawInput` when the title lacks it, then the numbered options; its fingerprint is 16 hex digits of a sha256 over the session id, the request's ordinal in the session, the tool call id and the options, so the same call asked twice gets a new one. `respond` answers the first request waiting: `stale` when the fingerprint is not its, `unknown_option` for a number it does not offer, `not_blocked` when none waits, `auth` for the login block below; otherwise the option's `optionId` goes back as `selected`. A request made while another waits queues behind it, one the agent withdraws (its request's signal aborts) is dropped, and any left at a turn's end is answered `cancelled`, as is every one a handover's cut finds waiting or that the turn asks after it.
- **`prompt`**, which sends the brief and `reply`, goes only between turns: it throws `PromptRefused` while a turn runs, before the session is open and after the process exited. It returns once the request is sent; the turn's end comes as a status.
- **A missing login is a configuration error.** The 2026-11-08 probe (card `acp-handover-probe`) found that without `USER`, `initialize` and `session/new` succeed and only `session/prompt` fails, with -32000 Authentication required. A -32000 from `session/prompt` or `session/new` is reported as `blocked` with `kind: "auth"` and a `msg` that calls it a configuration error, names the call refused and the `HOME` and `USER` soma started the agent with, and says what the refusal leaves; it is logged as `[soma] acp: ...`. The bridge hands every kind=auth block to the human with a question notice and an escalated decision, without waking the model, so the job is not recorded as failed. What a fix reaches differs by call. After a refused `session/prompt` the session is open and no turn runs, so a `reply` goes, and finds a login the human has made since if claude-agent-acp reads it anew. After a refused `session/new` the job has no session: `prompt` throws `PromptRefused` ("has no session yet") and nothing sends `session/new` again, so the job stays blocked with kind=auth for good. Either way `HOME` and `USER` are fixed when the process is spawned, so a changed environment reaches an agent only when soma starts it, after soma restarts with it. After a refused `session/prompt`, a reply after the restart wakes the job's agent in its session, spawned with the new environment ("Across a soma restart", below), if a prompt of it ever ran: a job whose brief was refused has no transcript, so no session to load, and the reconciliation records it as `error` "agent is gone", as it does after a refused `session/new`.
- **`readResult`** reads the session's claude transcript, `~/.claude/projects/<cwd realpath with every non-alphanumeric as ->/<ACP session id>.jsonl`, with `readLastRecord`, as rex and tty do. After a turn's end it waits, up to `replyMs` (2 s), until the transcript ends on a record other than the one it ended on when the turn was prompted and does not end awaiting the reply; past that it returns what is there and reports the end again `recheckMs` (10 s) later, as tty does. A stopped agent's transcript is still read, after a restart too, since the sessions file names it, and a dormant one's (below) without starting it.
- **`screen` has no pane to read**, so `readScreen` draws the tail of the transcript as claude draws a conversation (`drawTranscript`, `src/adapters/acp/screen.ts`): prompts after `>`, replies and tool calls after `●`, each tool's result under its call after `⎿`, cut at 6 lines, thinking left out, and below it the permission request waiting, if any. Most of a real transcript's bytes are records outside the conversation (API request blobs, attachments, snapshots), and the first real run drew only the last reply from a 64 KiB tail, so the window starts at 256 KiB and doubles until it draws 400 lines, the most `screen` shows, or holds the whole file, up to 16 MiB.
- **`stop`** records the agent stopped (above), sends `session/close` (waiting 3 s at most) and kills the process, and reports nothing; a dormant agent's records it stopped and starts nothing. The ACP port alone has no foreign agents.
- **Defer, reclaim and resume (milestone 3).** The core's rules ("Agent-deferred instructions") did not change, and neither did the AgentPort contract; this is what the adapter gives them. `soma defer` works in the agent's Bash through the environment above, and the reclaimer's `stop` ends the process, so a waiting agent holds no slot, and its job ends `stopped` and is not reported gone.
  - **`resume`** takes the session from the sessions file, which the port holds in full from the moment it is made, so it works on the same soma and on the next, where the stopped agent was not dormant. It starts claude-agent-acp in the recorded cwd with the environment `start` gives, and sends `initialize` and `session/load` with the recorded ACP session id, as a wake does, but past the hangar cap; it counts against the cap for whatever starts next. The stopped mark comes off only once the session has loaded, so a load that fails leaves the agent as it was.
  - **Listed idle, reporting nothing.** Once loaded, the agent is listed `idle`, under a seq of its own, and no status is emitted. The deferral's `ready` phase reads the listing, and that is all it needs. An idle reported to the bridge would send a brief the job still holds and could record a turn; with none, the next observation is the `working` of the instruction, so neither the stop nor the resume records a turn, and the turn the instruction starts is recorded as any other.
  - **How it refuses.** A name already listed, running or dormant, or being resumed, throws, with no process started, and `start` refuses one being resumed. No entry, an entry of another session id than the job holds, or no transcript (claude refuses such a session with -32002) throws `NotImplemented`, the one thing the core takes for an agent side that cannot start this agent again, so the deferral ends `gone` with its old notice. A worktree that is gone or a `session/load` that fails throws what happened, its process ended, so the deferral ends `unresumed` with a notice naming it. In each case the agent is not listed and stays stopped.
  - **A crash in the resume.** Before the mark comes off, the rerun finds the agent unlisted and resumes it again. Between the mark coming off and the prompt, a few milliseconds, the rerun finds it dormant, with no status, so the deferral's `ready` phase ends it `failed` after `readyMs` with one notice; nothing is sent twice, and a reply wakes the agent. A job still `due` at a restart, whose agent was never stopped, has a dormant agent, which holds no slot either: its deferral finds it listed, and the prompt wakes it, held to the cap as any wake is, and retried by the deferral when refused.
- **Across a soma restart (milestone 2).** soma's exit, clean or not, closes the pipes to its agents; claude-agent-acp exits on stdin EOF (`acp.closed` in its `dist/index.js`) and takes its Claude CLI and the CLI's MCP servers with it, so no agent outlives soma. Whatever turn ran then is lost with the process; the transcript keeps what claude wrote of it. Nothing in soma stops a finished job (only a reclaim calls `stop`), so the sessions file holds every job soma ran and did not stop, and starting them all again at a restart would fill the hangar with jobs no one uses, after which every dispatch fails. So the next soma's port, made in `openAgentPort`, reads `<db>.acp-sessions.json` and lists each entry not marked `stopped` whose transcript exists as **dormant**: under its name and soma's session id, with no process and no status, which is no claim (no turn of it runs, and what ran last is the core's to know). An entry with no transcript never ran a prompt, and claude refuses to load such a session (-32002), so it is not listed: the reconciliation records an unfinished job as `error` "agent is gone" with its notice, as before, and the port logs `[soma] acp: agent <name> is not listed after the restart: ...`. Entries stay, so every restart reads them again.
  - **Waking.** The first `prompt` to a dormant agent (a `reply`, a deferred instruction, the bridge's brief) wakes it. It is held to `hangarCap` as `start` is, and refused with `PromptRefused` "hangar is full" otherwise, staying dormant; a dormant agent counts against the cap only while it wakes and once it has a process. The port checks that the cwd still exists, spawns claude-agent-acp there as `start` does (soma's environment now, the same `SOMA_AGENT`, socket and `PATH`), sends `initialize`, checks it offers `loadSession`, and sends `session/load` with the recorded ACP session id, that cwd and no MCP servers, each answered within `startMs` (30 s); then the prompt goes as for any agent. claude-agent-acp answers from the session's transcript, replaying its history as `session/update`s, which are not read, and the model answers from it. A prompt that comes while the agent wakes waits for the same wake, then finds the turn under way and is refused. A wake that fails (-32000, -32002, the process dying, the worktree gone) kills the process, refuses the prompt with `PromptRefused` naming why, reports `error` with the same reason, which ends the job error, and logs `[soma] acp: agent <name> is not woken: ...`; the agent stays dormant, so a later prompt tries again. `readResult` and `screen` read a dormant agent's transcript, `respond` finds nothing waiting, and `stop` records it stopped, none of them starting a process. `start` refuses a dormant agent's name, whose session goes on with a reply.
  - **Through the core.** `main.ts` hands the names the port listed dormant (`dormant()`, outside the AgentPort contract, which did not change) to `reconcileDispatches`. A listing with no status changes no job, so each keeps the status, message and outcome soma last recorded: a job `done` or `error` before the restart stays so and records nothing. A job recorded `working`, or blocked other than kind=auth, had its turn cut. In the commit of the reconciliation it becomes `done` with `msg` "the turn was cut short when soma restarted" and outcome `未知`, and forgets the block it handed over; a `soma.dispatch.done` with outcome `未知` and `notified: true` (the notice below tells it) is appended. That happens once: the next restart finds the job done. A job that still holds its brief keeps it until its agent next works, which drops it: a dormant agent reports no idle, so a brief that went just before a crash, before the commit that lets go of it, is not sent again.
  - **One notice per restart.** In the same commit, one notice names every job that was idle, working or blocked and came back dormant, says that a reply goes on in its session, and names those whose turn was cut: class `action` when a turn was cut, else `ambient`. A done or failed job is not named, and a restart with no job to name appends no notice. The status soma recorded is what tells a cut turn, so a turn that ended or began in the moment before soma went down, before its status was committed, is named wrongly.
- **Handing a job over to rex (card `acp-show-in-rex`, milestones 1, 2a and 2b).** The human asks to see a job; the turn it runs is cut, if it runs one, the job's ACP session closes, and the same conversation goes on in a window of soma's rex hangar, for good. From then on it is a rex job of soma's: `jobs`, `screen`, `respond`, `reply`, the event bridge and a deferral handle it as they handle any. `agentAdapter: "acp"` with a hangar session named (see "Configuration") turns this on. The AgentPort contract did not change: the handover is new interfaces beside it, in `src/ports/handover.ts`.
  - **Two sides below the core.** The core takes one AgentPort. `src/adapters/handover/agent-port.ts` is one, over the ACP port (`SessionGiver`) and the rex port (`SessionTaker`), which it knows through `src/ports` only, since adapters do not import each other, and `openAgentPort` wires them. Every job starts on ACP and is routed by where it is: a name the ACP side released goes to rex, any other to ACP. The ACP side's sessions file is the record of which, and for a handover cut short the file and the hangar together, so a restart routes each job as the soma before it did, and a job carries no adapter of its own in the dispatch list. Foreign agents all come from rex, so a soma with a hangar lists the human's panes as a rex soma does; only the `SessionGiver` and `SessionTaker` calls touch both.
  - **A job not handed over has nothing on rex.** No window, nothing of it in `foreign_agents`, and with no job handed over the listing asks rex nothing at all, so a rex server that is down costs ACP jobs nothing but the foreign watch's log lines. A window of the hangar that merely has a job's name is neither listed as the job nor heard as it: only statuses and windows of names handed over pass. With one job handed over, the listing needs rex, and one that fails fails the whole listing, as it does on rex: a failed listing is doubt, never "not listed", so the job is not reported gone; startup then fails on it, which restarts soma under launchd until rex is back. A job whose handover was cut short does not fail a listing: see "A handover cut short".
  - **The tool.** `show_job` (`src/core/extensions/dispatch/index.ts`), `replay: "unsafe"`, takes a card, and its description says that it interrupts a running job and cancels a pending prompt, so it is only for when the human asks to see, show or take over a job. It returns `handedOver: true` with the window, its session's label, the session id and `ready`, or `handedOver: false` with `refusal` and `reason`; either way with `cut` when something was cut. Refused with nothing done: an unknown card (`unknown`); a soma with no rex hangar (`no_hangar`); a job not on ACP, as one already handed over or any job of a rex, herdr or tty soma (`not_acp`); a job blocked on a login, in a session still opening, waking, or one a deferral has in hand or that soma stopped (`not_at_rest`), since a reclaim would close the window the human just asked for; and what claude could not go on with, or a hangar that cannot take it (`cannot_resume`): no transcript, as a job that never ran a prompt; one holding no conversation yet, as a job whose prompt claude has not written, of which `claude --resume` says "No conversation found"; no model named by a reply or reported as the session was created; a worktree gone; a window of the job's name already open; a rex that does not answer. Each of these is checked before anything is cancelled or closes. A sessions file that will not take the mark refuses with the same `cannot_resume` before anything closes, past any cut. Past that point the refusals say the ACP process has ended: a window rex refused, which leaves the job on ACP, and one whose fate is not known yet, which leaves it undecided until a notice tells the human which side it is on ("A handover cut short").
  - **The move.** The ACP entry is marked `handingOver: true` first, with the hangar and the time, so nothing on the ACP side lists, wakes, resumes or starts that name again, on this soma or the next; `session/close` follows, and the release returns only once the process has exited (SIGTERM, then SIGKILL after `closeMs`), since the window must not write the transcript beside it. A mark that does not reach the file refuses the handover with the reason and opens no window: the agent is put back as it was, its process untouched, since a job unmarked after a restart would wake on ACP beside the window's claude, two writers on one transcript. The check that the job is at rest and its removal from the ACP side are one synchronous step, and a prompt already under way finds the agent stopped and is refused. Then one window opens, `focus: false`, named after the card, with an interactive shell typing the dispatch's environment and `claude --resume <ACP session id> --model <model>`, in the session's cwd, a realpath since `start`. Once `take` returned, the mark becomes the final `handedOver: true` (`confirm`). A file holding `handedOver: true` and no `handingOver`, as a soma of milestone 1 left it, is final as well: it is routed to rex with no look at its block and is never rewritten.
  - **A job working or blocked (milestone 2b).** As the human decided: a turn running is cut, a permission prompt waiting is cancelled, and the job moves at once. Nothing else differs from the move above, which comes after the turn has stopped.
    - **The cut** (`cut`, `SessionGiver`, in the ACP adapter). The job is held first, as any job moving is. `session/cancel` goes out and every request waiting is answered `cancelled`, as the protocol has a client do; one the turn asks after that is answered the same, so a turn being cut never blocks again. Then the prompt's response is waited for, up to `TURN_STOP_MS` (35 s, `cutMs` in tests), past the 30 s after which claude-agent-acp forces a wedged interrupt over itself. Only then does the mark go on. A job at rest gets no cancel and is told nothing was cut. Everything refused with nothing done, above, is checked first, so none of it cancels anything.
    - **A turn that does not stop in time.** `not_at_rest`, saying so and naming any prompt cancelled; nothing closes, no window opens and the job stays on ACP, reported `working`, not `blocked`, since no request waits any more, so the block handed to the model is forgotten as for any other status. The cancel stands: a later `show_job` waits for the same turn with no second cancel, and when the turn stops the job goes idle and the turn is recorded once, with outcome `未知` and no notice, since a cut turn's `readResult` gives its last record with no text. So no outcome is read off what it wrote.
    - **A turn that ends by itself as the cancel goes out.** A stop reason other than `cancelled` means the turn finished, so nothing was cut: `not_at_rest`, saying nothing was cut, nothing closes, the turn is recorded as any is, with the outcome it states, and a second `show_job` moves the job at rest. Handing over at once would have lost the turn's record, or claimed a cut that did not happen.
    - **While it moves, the job reports nothing.** From the cut until the caller has recorded how the handover ended, the two-sided port passes no status of the job from either side, so a cut turn's end is not read as a finished turn and a window's idle cannot reach a job still recorded working, which `observe` would read as one. `show_job` records inside the move (`handOver`'s `record`). The port then lists the job and passes what it reports now on as the observation it is, unless something newer has gone out since; so a window at work or blocked is told as for any rex job. A job a later look puts on rex is held the same way until the handover bridge has answered.
    - **What is left when it does not land.** A turn cut for a handover that then fails is over all the same: the job is `done` with `msg` "the turn was cut short by a handover that did not land" and outcome `未知`, with a `soma.dispatch.done` marked `notified`, and one notice in that commit says what was cut and quotes the refusal (`commitCut`). That holds for a mark that would not write, whose process lives on (its idle then records nothing, as done to idle does not), a window rex refused and a take left undecided, whose later landing or return does not tell the cut again.
    - **A read or a record that fails at the commit.** The move's commit reads what the transcript ends on, which can fail: rex's `readResult` makes calls. A commit with no last record to take leaves `resultUnread` on the job. A `working` status takes it off, since a new turn has begun and what it ends on is a real reply: its end is settled as any turn's against the `resultId` the job holds. A `complete` with no `working` before it takes what it reads as `resultId` and records no turn, since nothing can tell what ended on it from what a cut turn left; one that still reads nothing goes on waiting. Real claude resumed on a cut turn reports no `working` until the human or the model sends something (real run on 2026-11-09: idle for 60 s, then `working` 56 ms after the reply went in), so no cut turn is recorded this way, but for the status queued behind a move that "What the telling does not promise" names. A record that fails is said again through the handover bridge, as a landing that was not cut short, so the job takes the window's session and the human is told once, with the cut read off the status recorded; what the window reports waits for that (`unrecorded`). `show_job` has said `handedOver: true` all the same, since the job has moved.
    - **A telling that fails.** Saying a job's landing to the core can fail in two ways: rex does not answer the look at its window (`holds`), or the bridge's commit fails its listener. Every job handed over is told again at each startup, so the first reaches a job recorded long ago as well as one that is not. Either way the job is held in `unrecorded`, its window reporting nothing, in a status or a listing, and its next status tries the telling again, with no timer and one try at a time. A job that already holds the session is told nothing by it, so no retry tells a recorded job twice; one not yet recorded takes no status until its commit lands, and is told once. A try that answers clears the hold, and every status kept goes through in order, the one that tried it among them. A try that fails keeps the hold and the statuses for the next. After a failed look any status tries again, the status watch's first look included, so a job already blocked as soma restarts reaches the model once rex answers. After a failed commit only a status other than the one the last listing withheld does: the watch's first look repeats what the startup's listing withheld, which the reconcile went by. Every listing moves that mark (`listed`), a deferral's poll among them, so a new status a listing read first tries nothing either, and the job waits for the one after it. So a job stays held until a status arrives while rex answers, or, after a commit that failed, until a new status finds the commit landing or the next soma says it again, whatever the reconcile finds; until then its listing has no status, and a job whose window says nothing new stays so.
    - **The wake the model has pending.** A prompt's block may have woken the model, whose `respond` then comes too late. While the job moves it is refused `not_blocked` with the reason beside it; in the window `not_blocked`, or `stale` if another prompt is on screen, since rex's fingerprint is read off the screen and could not be ACP's; on ACP after a refusal `not_blocked`. Nothing is answered into the window. Nothing keeps the model from calling `escalate` on it instead: that notice would ask about a prompt no longer there.
    - **A crash during it.** No in-memory state is needed, since nothing of the cut reaches the core until its end. Killed after the cancel and before the mark: no mark on disk and the job still recorded `working` or `blocked`, so it is dormant with a cut turn, marked over and told by the restart's `dormantNotice`, as any turn a restart cuts. Killed after the mark, 2a's resolution applies. With no window, past the grace period at startup: the same `dormant()` and notice. With no window, within it: undecided, with `jobs` still reading what it read until the look (at most 60 s), and then a notice that the job is back on ACP and what was cut. With its window open, before the final mark or before the commit: on rex, one notice with what was cut read off the status recorded, the prompt quoted from it, and no turn recorded, since the handover bridge has recorded the move before the reconcile lists the window.
  - **A handover cut short.** Wherever soma can die or rex can fail, the sessions file and one hangar say where the job is, and it is on one side or undecided, on neither, taking no prompt: but not always, and "What a look cannot tell" names each exception. A window is known to exist when the hangar holds a block whose label is the entry's ACP session id (`holds`, `session.list_blocks`), in a window the listing reads as the job, a window of the job's name holding that block, anywhere in it (`session.view`, as `paneOf` finds a job's block), whose claude may have exited; the label is set as the window opens. `handingOver` is resolved by that look and only by it: such a window there, the job is on rex and the mark becomes final; rex answers and no block there, at or after the end of the grace period, the job is dormant on ACP with the mark off, as after a restart, and its next prompt goes on in the session. Anything else leaves it undecided. A window that is not labelled so, whatever its name, is not the job's.
    - **What the mark records.** With `handingOver`, the rex session id of the hangar (`hangar`) and when (`handingOverAt`): when it was written, moved on to when the take failed if one did (`markedAt`). Both come off with the mark. Every look goes to that hangar, whatever the config says now, and `session_not_found` for it counts as an answer: it holds no block. A hangar other than the port's own is read after `session.attach_all`, as `foreign` reads every session, and never attached to, since an attach is made again on every later connection, and one to a hangar gone since would fail them all (real rex 2026-11-08: `conflict` "stream is not attached" without `attach_all`, `session_not_found` with it). A mark from before these two, with neither, looks in the configured hangar and counts as older than any grace period.
    - **When it is looked at.** At startup, for each entry `handingOver`, before any listing, prompt or handover of the port goes on; in the running soma when `take` throws; at every listing, and before a `prompt`, `respond` or `handOver` of an undecided job, which then go on on the side the look finds, or refuse naming the reason that look found; and with no caller, once when a grace period ends, and while rex does not answer about a job, again 60 s after the last look and never before that job's grace period ends, until a look settles it. One look at a time: whoever comes while one runs waits for it. Status reading is no look: `jobs` reads the dispatch list.
    - **A take that failed.** A window found then is a handover: `show_job` says handed over, the core commits the move and tells the human once, and only then is the wait for claude made (`adopt`), so a trust dialog is answered as in `take` and a claude that has exited says `ready: false`. With none, it matters how it failed. Rex answering `session.new_window` with an error (`RexRpcError`), or a `take` that failed before asking (`takeable`'s reasons, or a read that failed), throws `TakeRefused`: no window can come of it, so the job goes back at once and the refusal is the one a window that will not open has always given, its reason saying the process ended, the job stays on ACP, and its next prompt starts it again in its session. Any other failure, a timeout or a lost reply above all, may still open a window, so the job is undecided and `show_job`'s refusal says so and why, and never that it stays on ACP.
    - **The grace period** (`HANDOVER_GRACE_MS`, 60 s, `graceMs` in tests). A client gives up on `session.new_window` after 10 s (`requestTimeoutMs`) while rex may go on working; a job given back then would start ACP on the session the late window's claude runs, two writers on one transcript. So for 60 s from when the take failed, a look that finds no block gives nothing back; a window that shows up within it puts the job on rex. It holds across a restart: a mark older than the period is resolved at once, a newer one waits out the rest, and one whose time is ahead of the clock, as after the clock was set back, counts as now, once, when it is read: otherwise it would wait out that much more, or overflow the timer. A soma killed mid-take counts from the mark, since it recorded no failure. A plain refusal followed by a rex that stops answering keeps the mark's time too. ### How agent-side adapters differ

The adapters on both sides are optional. Users pick them in the configuration to suit their own habits and weigh the differences in features themselves. The core assumes no ability is always there: when one is missing, the core degrades as the "Without it" column below says, and does not report an error.

| Ability | rex | herdr | native tty (M6) | ACP | Without it |
|---|---|---|---|---|---|
| Agents survive a soma restart | Yes, hosted by the rex server | Yes, hosted by the herdr daemon | No, the pty ends with soma | Their sessions do: the agent process is soma's child and ends with it; the next soma lists each job soma did not stop as dormant, with no process, and the first prompt to it starts it again with `session/load`; a turn running at the restart is lost, and the human is told once which unfinished jobs are dormant; one soma stopped stays stopped until its deferral resumes it | The reconciliation after a restart records unfinished jobs as the agent having gone missing and tells the human once |
| The human can watch the screen and take over by hand | Rex's client | herdr attach | No | No pane of its own; with a rex hangar named, `show_job` moves a job to a window there, for good, cutting any turn it runs, and it is a rex job from then on | Prompts can only be answered through a human-side adapter |
| Status source | 7501 sent by the agent itself, through rex's API | herdr's own detection | 7501 sent by the agent itself, with soma answering the probe and parsing it | The protocol: the prompt's response and `session/request_permission` | No status when the agent does not send 7501 |
| Reading the screen to answer prompts | `com.superlogical.terminal.format` | `pane.read` | soma's own terminal emulator, `@xterm/headless` | None needed: the request carries its options | Only the human can answer, by hand |
| Reading what a pane shows now (`screen`) | The same `format`, for jobs and foreign agents | `pane.read source: visible`, for jobs only | The emulator's screen and scrollback | The tail of the claude transcript, drawn as claude draws it | `screen` returns the adapter's error |
| Creating worktrees | The adapter runs git itself | herdr's `worktree.create` | The adapter runs git itself | The adapter runs git itself | Not applicable; all four have it |
| Refusing a duplicate name | No; relies on list-before-start | Yes | soma's own pty table, which blocks it within one process | soma's own process table, which blocks it within one process | Relies only on list-before-start |
| Reclaiming an agent that deferred, and resuming it at fire time | `block.close`, then `claude --resume` in a new window | No | Stops it, but cannot resume it | `session/close` and ending the process, then a new process with `session/load` | The deferral ends `gone` with one notice |

The human side is the same: Telegram can push and answer prompts with buttons, the terminal is seen only while it is in the foreground, and shikigami comes later.

Maintenance has priorities. The maintainer actively maintains the adapters they use, currently ACP with a rex hangar, Telegram and the terminal. Other adapters go through the tests when the core changes, but problems caused by upgrades of an agent or a platform are not guaranteed to be fixed.

### Agent state model: the OSC 7501 vocabulary

[OSC 7501 (Program Status Protocol)](https://www.superlogical.com/rex/docs/build/program-status) is a terminal escape sequence that lets a program report its own `idle`, `working`, `blocked` (with `kind` `permission`, `question` or `auth`), `done` and `error`. It can carry a base64 `msg`, and can report several hierarchical records with `id`. For background, see [Mitchell Hashimoto's article](https://mitchellh.com/writing/program-status-osc7501).

soma's support has two sides:

- **The internal state model uses the 7501 vocabulary directly.** herdr's idle/working/blocked/done map onto it, `blocked`'s `kind` is filled in by permission parsing, and cc-mobile's idle/running/requires_action are no longer used. This way the herdr mapping and future 7501 sources feed the same shape, and the event bridge's "`kind=auth` always goes to the human" rule is written directly on `kind`.
- **Sending: soma's terminal client reports its own status.** The root record is soma itself (`working` while a turn runs, `blocked:kind=question` when the assistant needs to ask the human, `done` when a report is written), with one child record `id=job/<task>` per dispatched job. Pi's emitter can be reused directly (`tui/src/program-status.ts`, 53 lines, root record only; `id` and `title` must be added), and Pi's own status mapping table is at `coding-agent/docs/terminal-setup.md:221-233`. This is part of M1 and costs about a dozen lines.
- **Receiving: the pty is herdr's, and soma does not read it itself.** For 7501 to reach soma, herdr must take it as a status source. Neither herdr 0.9.5's docs nor its release notes mention 7501; the matching proposal [herdrdev/herdr#5069](https://github.com/herdrdev/herdr/issues/5069) was closed on 2026-10-08 and redirected to discussions. Claude Code sends 7501 from 2.1.295, but only after the terminal answers a probe ([anthropics/claude-code#103022](https://github.com/anthropics/claude-code/issues/103022) asks for a switch that needs no probe). So "Claude Code inside herdr does not send 7501 today" is an inference, not tested. If soma later runs agents in its own pty (the ACP route), it must answer the probe and parse 7501 at that layer. That is what the M6 native tty adapter does. With the rex adapter, the pty is rex's, rex answers the probe, and Claude Code's 7501 reaches soma through rex's API (see "The rex implementation").

ACP is the second kind of agent interface. The human decided on 2026-11-08 that soma runs its jobs over it by default; it is built in milestones (see "The ACP implementation"), and for now it is selected with `agentAdapter: "acp"`, an unset `agentAdapter` still being herdr. According to the docs at [agentclientprotocol.com](https://agentclientprotocol.com):

- **stdio is the only stable transport**, with the client starting the agent as a child process. The spec does not say what happens to the agent when the client dies.
- **Whether a session can be resumed after a disconnect depends on the agent implementing it.** `session/load` and `session/resume` are both optional features.
- **Permission requests are structured** (`session/request_permission`), cleaner than herdr parsing the screen.
- **The stable version has no blocked state**; it only comes with `requires_action` in the v2 draft.
- **Claude needs an adapter**, `@agentclientprotocol/claude-agent-acp` (0.93.0 then; 0.100.0 on 2026-11-05; 0.101.0, pinned, since 2026-11-08), which wraps the Claude Agent SDK, not the Claude Code CLI itself ([agents list](https://agentclientprotocol.com/get-started/agents)); Gemini CLI supports it natively with `--acp`. The SDK is `@agentclientprotocol/sdk` (1.9.0 then, 2.4.0 on 2026-11-05, where the client side is `client().connectWith(...)` and a handler gets `{method, params, signal, agent}`).
- **claude-agent-acp can be reclaimed and resumed** (probed on 2026-11-05 with 0.100.0 and SDK 2.4.0, card `acp-agent-adapter`). `initialize` advertises `loadSession` and the session capabilities `close`, `resume`, `fork`, `list` and `delete`. After one prompt, `session/close` and killing the process, a new process accepted `session/load` with the same id and cwd, replayed the history and answered from it. The state is claude's transcript, `~/.claude/projects/<cwd realpath with / and . as ->/<session id>.jsonl`, appended to rather than forked; the adapter finds it by id under `CLAUDE_CONFIG_DIR` or `~/.claude`, so a session that never ran a prompt cannot be loaded. `initialize` lists no auth methods: it ran on the machine's Claude Code login, though only from an environment inherited from a Claude Code session, so a launchd environment is untested. It loads the user's global skills unless `CLAUDE_CONFIG_DIR` points elsewhere, and a new session wrote about 33k tokens to the cache. The SDK client resolves a -32002 from `session/close` as `{}`, so `{}` does not show the session existed.

Conclusion: there is no single main choice; the user picks. Interfaces where the terminal hosts the agent (rex, herdr) keep agents alive when the core restarts, and let the human switch into the pane and take over by hand at any time; the native tty lacks both, but needs no separate multiplexer. ACP runs the core's own jobs as children of soma: they end with soma, but a job's session outlives it, so after a restart the job is dormant, costs no process, and a reply goes on with its context, though not with a turn the restart cut. An agent waiting on a deferred instruction costs no process either, and is resumed in its session at fire time. Nothing closes a finished job yet, so every job soma did not stop stays listed.

## Configuration

soma reads a configuration file once at startup: the file named by the environment variable `SOMA_CONFIG`, or `~/.config/soma/config.json` when it is unset (`configPath` in `src/config.ts`). Unset, it reads prod's configuration, so a dev instance must set `SOMA_CONFIG` to its own configuration file, with a different `db` and no `telegram` (see the milestone "Resident service"). Each value comes first from the environment variable, then from the file, and finally from the default; the fields, their environment variables and defaults are all in `resolveConfig` in `src/config.ts`. If the file does not exist, only environment variables and defaults are used. When the JSON is broken, a field has the wrong type, or there is an unknown field, soma prints the file path and the field name and exits with status 1, rather than running on part of the configuration. Example:

```json
{
  "agentAdapter": "herdr",
  "herdrSocket": "/Users/me/.config/herdr/sessions/fleet/herdr.sock",
  "rex": { "sessionId": "session:01a1...", "socket": "/Users/me/Library/Application Support/rex/server.sock" },
  "mcpConfig": "/Users/me/.config/soma/mcp.json",
  "db": "/Users/me/.local/share/soma/soma.sqlite",
  "deferSocket": "/Users/me/.local/share/soma/soma.sqlite.defer.sock",
  "model": "claude-opus-5-5",
  "language": "zh-Hant-TW",
  "hangarCap": 4,
  "compactAt": 100000,
  "programStatus": true,
  "repo": "/Users/me/workspace/soma",
  "reposDir": "/Users/me/workspace",
  "reflection": true,
  "dream": { "model": "claude-opus-5-5", "periodDays": 7, "log": "/Users/me/Library/Logs/soma.log" },
  "anthropic": { "apiKey": "sk-ant-..." },
  "exa": { "apiKey": "..." },
  "telegram": { "botToken": "123456:ABC...", "chatId": 123456789 },
  "web": { "host": "100.101.102.103", "port": 8790 },
  "skillsDir": "/Users/me/.config/soma/skills"
}
```

- **`agentAdapter`, `herdrSocket` and `rex`.** `agentAdapter` (`SOMA_AGENT_ADAPTER`) picks the agent-side adapter, `"herdr"`, `"rex"`, `"tty"` or `"acp"`; unset, it is herdr, so a config written before rex keeps working, and `openAgentPort` in `src/agent-side.ts` is the one place that builds it. herdr reads `herdrSocket` (`SOMA_HERDR_SOCKET`). `"acp"` with a hangar session named, in `rex.sessionId` or `SOMA_REX_SESSION_ID`, runs jobs over ACP and hands one the human asks to see over to that hangar (see "The ACP implementation"); without one, acp runs alone, and a `rex` block it cannot use exits 1 naming the field, since under acp it is no longer ignored. Under herdr and tty the `rex` settings are not read. `rex.sessionId` (`SOMA_REX_SESSION_ID`) is the hangar session's id, such as `session:<uuid>`, and is required under rex, because the adapter finds the hangar by id, never by label (see "The rex implementation"); `rex.socket` (`SOMA_REX_SOCKET`) is the rex server's socket, by default `~/Library/Application Support/rex/server.sock`. `rex.label`, file only and optional, up to 128 characters, is the label of the session soma makes when the hangar it would use does not exist, `soma-hangar` when unset; the id of the session made is kept in `<db>.rex-hangar.json`, never in this file (see "A hangar that does not exist is made anew"). A label that does not start with `soma-` makes the hangar's jobs foreign agents to any other soma ("Foreign agents"). `hangarCap` applies to every adapter; rex counts the hangar session's blocks running claude against it (see "The rex implementation"), tty and ACP the agents they run. tty and ACP take no settings of their own; ACP keeps each agent's ACP session, and whether soma stopped it, in `<db>.acp-sessions.json`, next to the db as the defer socket is (see "The ACP implementation").
- **`compactAt`.** The root conversation's size in tokens past which it is compacted (`SOMA_COMPACT_AT`), a positive integer, 100000 by default; anything else exits 1 naming the field or variable. See "Compacting the root conversation".
- **`repo` and `reflection`.** `repo` is soma's own git checkout, where the reflection reads `.obsidian.yaml` and sends its code-change cards; unset, it is the directory the code runs from, which prod must override once it runs from a release. `reflection: false` leaves out the daily reflection and its `open_card` tool, which dev sets so a dev db does not open cards. A reflection task a db already holds stays `pending` while it is off and the same task resumes when it is turned back on, without a second one being created (checked 2026-10-26 on a copy of a dev db).
- **`dream`.** The periodic review of soma's own records (see "Dream"), in the config file only. Absent or `false`, there is no dream task and no cost; dev leaves it off, so a dev db pays for no review of its own noise. An object turns it on: `{ "model": "claude-opus-5-5", "periodDays": 7, "log": "/Users/me/Library/Logs/soma.log" }`, where `model` (an Anthropic model id, through the same provider and key as the root) defaults to `claude-opus-5-5` (`DREAM_MODEL`), `periodDays` (a positive integer) to 7 (`DREAM_PERIOD_DAYS`), and `log`, soma's log file, is optional: unset, the dream reads no log. `true`, any other value, a field of the wrong type or an unknown field exits 1 naming it (`resolveDream` in `src/config.ts`).
- **Paths do not expand `~`.** Write absolute paths; a relative `db` path is taken from the directory at startup.
- **The model key is not written into `process.env`.** `anthropic.apiKey` is passed in through pi-ai's `createModels({ authContext })`: soma's `env()` first asks pi-ai's default environment variable lookup, and returns the key from the configuration file only when `ANTHROPIC_API_KEY` is unset. The provider looks for `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_OAUTH_TOKEN` and `ANTHROPIC_API_KEY` in that order, so any of these environment variables overrides the configuration file. pi-ai's credential store is not used, because credentials stored there override environment variables (the Credential Store section of the pi-ai README), which would reverse the precedence.
- **Permissions.** When the configuration file holds a key or token and is readable by the group or others, startup prints a warning; please `chmod 600` it.
- **`web`.** The web page (M7) has two modes, and exactly one is chosen by which fields are set. It is on only with `web.port` (`SOMA_WEB_PORT`) and one of them; with neither it is off, as before.
  - **Tailnet-IP mode**: `web.host` (`SOMA_WEB_HOST`) and the port. The host must be one tailnet IP address, in 100.64.0.0/10 or fd7a:115c:a1e0::/48 (`tailscale ip`), or soma exits 1 naming the field: the page has no login, so it never listens on a wildcard, on loopback or on the LAN. It serves plain HTTP, and the upgrade is refused unless `Host` is that address and `Origin`, when sent, is the page's own. It needs the tailnet up when soma starts.
  - **Serve mode** (decided 2026-11-05): `web.origin` (`SOMA_WEB_ORIGIN`), `web.login` (`SOMA_WEB_LOGIN`) and the port. soma listens on `127.0.0.1:<port>` and nothing else; the human runs `tailscale serve` (soma neither runs nor manages it) to publish that port on the MagicDNS name over HTTPS, for example `https://nick-mac-mini.tail361ef.ts.net:8445`. The origin must be `https://` with a host, an explicit or default port and no path (a default port is dropped from the canonical form, as a browser's Origin and Host drop it); the login is the one `Tailscale-User-Login`, such as `musingfox@github`, that may use the page. Every HTTP request and every upgrade must carry that header with exactly that value and a `Host` equal to the origin's host[:port], else 403 (the upgrade is refused before the WebSocket handshake), and an upgrade's `Origin`, when sent, must be exactly the origin. serve strips a client's own `Tailscale-User-Login` and sets its own from the caller's tailnet identity ([Tailscale Serve, identity headers](https://tailscale.com/kb/1312/serve)), and its documentation advises trusting the header only when the app listens on localhost, which is why this mode listens on nothing else.
  - **Config refusals**, each exiting 1 with the field named: `web.host` set together with `web.origin` or `web.login` (the modes do not mix; `web.host` is still refused when it is loopback, a wildcard or a LAN address); `web.origin` without `web.login`, or the reverse; an origin that is not `https://`, has no host, or carries a path, query, fragment or credentials.
  - **Accepted risk**: serve mode trusts the header, and a local process can connect to `127.0.0.1:<port>` directly and forge it. The page has no other login, so in serve mode it is as strong as the machine's local users; the tailnet-IP mode instead lets in any device on the tailnet.
  - **Why a second mode**: the later M7 steps want HTTPS (a secure context for the service worker, Web Push and the microphone), which plain HTTP on a tailnet IP cannot give, and `tailscale serve` terminates it with a certificate for the MagicDNS name. Listening on loopback also removes soma's boot-order dependence on the tailnet: the tailnet-IP mode cannot bind before tailscaled has given the node its address, while loopback always exists and serve connects when the tailnet is up. Rejected: Cloudflare Tunnel, which would make the page public on the internet, where the tailnet keeps it reachable only by the human's own devices.
  - A page that cannot listen (the tailnet down at boot in the tailnet-IP mode, the port taken) is logged and soma runs without it, with no retry until a restart. The static allowlist, the 1 MiB message limit, ping and terminate, and prompt shutdown on SIGTERM are the same in both modes.
- **`reposDir`.** The folder whose direct children are the git repos `soma dispatch` may start a job in (`SOMA_REPOS_DIR`); it must be an absolute path, or soma exits 1 naming it. Unset, every `soma dispatch` is refused. See "Decisions made", 2026-11-17.
- **`deferSocket`.** The socket `soma defer` and `soma dispatch` talk to (`SOMA_DEFER_SOCKET`), by default `<db>.defer.sock`: one soma owns one db, so prod and a dev instance never share a socket without any setting. It is bound 0600. A socket file a killed soma left is replaced; a live one, or a path that is not a socket, is refused, and soma then runs without `soma defer`. macOS caps a socket path at 104 bytes. Agents read the path from `SOMA_SOCKET`, not `SOMA_DEFER_SOCKET`, so a dev soma started from an agent's shell does not take prod's socket as its own.
- **`push`.** Each interface's push policy, in the config file only (no environment variable): `push.telegram`, `push.terminal` and `push.web`, each a preset name (`"instant"`, `"ask"` or `"summary"`) or a table setting all three classes, such as `{ "action": "ring", "outcome": "hold", "ambient": "log" }`, with the policies `ring`, `quiet`, `hold` and `log` (see "Whom to push to when there are several interfaces"). An interface left unset is `instant`, so a config without `push` pushes as before. `push.summary.idleMinutes` is how long the human types on no interface before what is held is summarized: a positive number of minutes, fractions allowed so a dev run can cut it short, 30 when unset (`SUMMARY_IDLE_MINUTES`, `resolveSummaryIdle`). An unknown preset, class, policy, interface or `push.summary` key, a table missing a class, or an idle time that is not a positive number, exits 1 naming its path, such as `push.telegram.outcome` (`resolvePush` in `src/config.ts`). Example: `"push": { "telegram": "summary", "summary": { "idleMinutes": 30 } }`.
- **`skillsDir`.** Where soma's skills are (`SOMA_SKILLS_DIR`), by default `~/.config/soma/skills`; the human chose a directory under `~/.config/soma/` on 2026-11-07, and a deeper layer waits for other kinds of content to need one. A skill is Markdown in the [Agent Skills](https://agentskills.io/specification) format, a directory holding a `SKILL.md` whose frontmatter has a `description`, the form pi-coding-agent and Claude Code read; a new tool is still code in this repo, never a TypeScript file loaded at runtime with soma's credentials (decided with the human on 2026-11-07). ## Next steps for interfaces: interaction and reading

Decided on 2026-10-22: the next interface is not chosen by channel (cc-mobile, shikigami). It is judged in two directions instead: the way of interaction (buttons, options, voice) and the way of reading (images, web pages and reports beyond plain text). shikigami is at heart a desktop assistant; its voice belongs to the way of interaction, and its presentation can share one set of web pages with cc-mobile.

According to the Bot API 10.3 docs (2026-08-24), Telegram itself can take most of the needs, so the client socket (M4) and a separate web client are pushed back further:

- **Interaction**: an inline button's `callback_data` is limited to 64 bytes, and after a press the original message can be rewritten with `editMessageReplyMarkup` ([Bot API](https://core.telegram.org/bots/api#inlinekeyboardbutton)); voice is downloaded with `getFile`, up to 20 MB, with no transcription ([getFile](https://core.telegram.org/bots/api#getfile)).
- **Reading**: `sendRichMessage` (new in 10.1) supports tables, headings, collapsible sections and buttons, up to 32,768 characters ([sendRichMessage](https://core.telegram.org/bots/api#sendrichmessage)); which client versions render it is not documented. Plain `parse_mode` has no tables or lists and is limited to 4096 characters. A Mini App only requires an HTTPS URL, and `initData` is validated locally with the bot token ([Web Apps](https://core.telegram.org/bots/webapps)); whether a connection over Tailscale alone works is not proven.
- **The core does not change**: the core still produces one structured text answer, the adapter turns it into a rich message, and "the adapter decides how to present it" stays.

The order is as follows, each step with one observable outcome:

Since 2026-11-17 an agent may end that reply listing 2 to 4 options, which the human answers with one press, sent to the agent with no model round, and which soma's model is shown in its `job_questions` section for an answer the human types (see "Options a job's agent lists"). 2. **Answer stuck prompts with Telegram buttons.** A prompt the model hands to the human comes with option buttons; after the human presses one, the core sends it straight to the agent without running the model (done 2026-10-22; the acceptance on the phone has run).
3. **Reports use rich messages.** First test the rendering on the phone.
4. **Receive voice and turn it into text.** Speech-to-text runs on the GPU workstation.

### Whom to push to when there are several interfaces

Decided on 2026-10-23. Pushing on every interface is noisy, and adapters do not import each other, so they cannot see that the human is on another interface right now. So the core decides whom to push to, based on the `entry.kind` of the human's latest input.

- **Only pushes the core starts are covered**: `notice`, and the failures of the `PUSHED_FAILURES` turns. A turn the human started still goes back only to the adapter that started it. A question soma asks with `ask` in such a turn is part of that reply on the interface the turn came from (see "A question asked in reply" below).
- **Push target**: the interface with input in the last 15 minutes; if none, the default channel, Telegram. The other interfaces still get the content but do not ring; Telegram uses `disable_notification`.
- **Escalation**: if within 15 minutes after a `question` or a failure is pushed the human has neither answered that prompt nor typed on any interface, push once more to Telegram; when the target was already Telegram, there is no escalation. A question about a job is answered once the job is past its fingerprint, and one about a foreign agent once the agent is past the prompt told ("Foreign agents"). Reports do not escalate; if nobody reads them, they stay in the history.
- **Put away once answered**: when a prompt is answered on one interface, the same one on the other interfaces loses its buttons (Telegram uses `editMessageReplyMarkup`).
- No guessing of user preferences: there are too few signals, and the cost of a wrong guess is a missed notice that needs the human. The work is in the obw card `multi-interface-push-target`.
- **Whether a foreign agent is pushed at all is not this rule's** (2026-11-05). This rule knows only which of soma's interfaces had input last, not whether the human is looking at an agent's pane in the terminal; the agent side tells that ("Foreign agents", milestone 2). Once a foreign push is due, its notice goes through this rule like any other.
- **Levels (decided with the human on 2026-11-05, card `push-levels`).** Every message soma starts gets a class, each class gets a policy per interface, and the config sets the table. Classes: `action` (it waits on the human), `outcome` (how a piece of work ended), `ambient` (what soma did on its own). Policies: `ring` (send now and ring), `quiet` (send now without ringing), `hold` (keep for the next summary) and `log` (history only; the interface does not show it). Presets fill the table: `instant` rings every class; `ask` rings `action` and logs `outcome` and `ambient`; `summary` holds every class, `action` included, as a real do-not-disturb (the human accepts that a blocked agent can wait for the summary); a question soma asks in reply to the human's own message is not a push and is not held there (see "A question asked in reply" below). A summary is sent after N minutes with no input from the human while held messages exist, and at fixed times, both set in config; the model writes it in one round, questions first, as the digest does today. Escalation never fires under `summary`, since a held question shows up in the next summary; `instant` and `ask` keep it. The ten-minute digest is folded into `summary`: a finished job becomes an `outcome` message the levels govern, and the digest extension goes away once `summary` replaces it. The policy is set per interface in the config file only (for example the web page `instant` and Telegram `summary`); there is no chat command and no switching by time. Built in milestones: `push-levels-classes` (classes, policies, `instant` and `ask`), then `hold`, `summary` and its triggers.
- **How the push target combines with the policies** (decided by the human on 2026-11-05). Each interface's own policy is a ceiling on what it does with a message of that class. Only the push target rings, and only when its own policy for that class is `ring`. Every other interface whose policy is `ring` or `quiet` shows the message quietly; an interface at `log` does not show it. When the target's policy does not allow ringing, nobody rings: the ring never falls through to another interface. Escalation stays as it is for `instant` and `ask`, and follows Telegram's policy for the message's class: when that policy is `log`, no escalation is kept. An answer to a turn the human started still goes back only to the interface that started it, whatever the policies; `forwarded` notices and `job`/`run` events are not pushes.

## Decisions made

Decided on 2026-10-18:

- **Run on Node first.** Pi officially supports only Node; each of the three Bun APIs in the reused code is a one-line swap, and there is no storage adapter to maintain ourselves. The assessment for moving to Bun later is below.
  - Benefits: the same toolchain as cc-mobile; fast startup; it can be packed into a single executable.
  - Costs: a `bun:sqlite` adapter must be written and maintained (the Node version is 201 lines); neither pi-durable's whole harness nor pi-ai's streaming is verified on Bun; pi-durable is experimental, so every upgrade must be checked once on each runtime.
  - What the switch touches: add a SQLite adapter, change the three node calls back to Bun APIs, and rerun M0's smoke test and M1's `kill -9` acceptance.
  - When to reassess: after M2 is done, once the API surface the harness uses is known.
- **Model authentication uses an Anthropic API key.** For the reason, see "External dependencies".
- **When an agent is stuck, the model judges whether to hand it to the human**, except for `kind=auth`; the judgement and the reason are recorded in the dispatch list.
- **Completion reports go through the check every ten minutes**, and the model is woken to write a short report only when there are newly finished jobs. Exception (2026-10-23): when the outcome is `需要你` or `失敗`, or it is a `完成` the human touched within ten minutes, the event bridge notifies the human directly without waking the model, because someone is waiting; in the Telegram acceptance on 2026-10-22, the report arrived nine minutes after the agent finished.

Decided on 2026-10-24:

- **The adapters on both sides are optional.** Users pick them to suit their own habits, and even the native tty must be workable; different adapters have different features, and users weigh them themselves (see "How agent-side adapters differ"). A rex adapter (M5) and a native tty adapter (M6) are added, and the herdr adapter stays. AgentPort already uses the OSC 7501 vocabulary (`src/ports/agent.ts:1`), and Claude Code reports 7501 natively inside rex, without `herdr integration install claude`. For rex's tested facts and the gaps to fill, see "The rex implementation".
- **Maintenance has priorities.** The maintainer actively maintains the adapters they use; the others go through the tests with core changes, but problems caused by upgrades of an agent or a platform are not guaranteed to be fixed.
- **The core is not tied to any one interface.** soma may later be opened to others, whose habits need not match the maintainer's. So no interface name appears in the ports or the core (removing the `herdr:` prefix in M5's preparatory changes is for this), interface-specific approaches stay in the adapters, and others can write an adapter for their own terminal.
- **cc-mobile is no longer needed.** The reason for not reworking it is that its `server/herdr/` is about 5.7k lines of non-test code, herdr's vocabulary has seeped into its wire protocol and push logic, and reworking it would cost close to a rewrite. The `cc-mobile-socket/` and `cc-mobile-launch/` adapters soma had planned are also cancelled. cc-mobile's user-facing features fall into three groups:
  - **soma takes over**: dispatching into the hangar, pushing when stuck, and picking permission or question options for dispatched agents (Telegram buttons). Completion notices: the ten-minute digest plus urgent immediate notices replace cc-mobile's 45-second merged push.
  - **The terminal client takes over**: pure interface features such as mirroring a session, streaming display, quick actions, autocomplete and themes, handled by Rex's client.
  - **Dropped**: answering permissions on panes the human opened themselves, sending free text to any agent, interrupting, picking a directory on the phone to open a session, sending images, writing the audit file, hangar-offline push, and `GET /api/cards`. The first three will be taken over by Rex for iOS once it is available; the rest are no longer offered.
- **The gap on the phone.** Rex for iOS is not yet in public testing, and push to the phone does not exist yet. Until they are available, the phone can only answer prompts of agents soma dispatched, through Telegram; when an agent the human opened in a terminal gets stuck, the phone gets no notice and cannot answer it.

Decided 2026-10-27:

- **A completion is identified by the transcript's last record, not by timing.** A turn whose transcript ends on a user record recorded a new `未知` turn at every re-stamp, and two adapter-level fixes that told a re-stamp from a new turn by timing both left holes. So the contract changed instead: `AgentResult` is `{ id, text? }`, `id` the `uuid` of the transcript's last record, whoever wrote it (see "Event bridge", M5-2d).
- **Web search and page fetch are two read-only core extension tools, not MCP servers.** Decided with the human for the `web-search` card. The rule that external capabilities come in through pi-mcp ("What the core is made of", External tools) gets one exception: a tool that only reads, has no side effects, and whose output soma must shape may be a core extension, with the provider's details kept inside that extension.
  - **Search** is `web_search`, which POSTs to Exa's `/search` with `contents.highlights` and returns title, URL, date and highlights per result ([Exa highlights](https://exa.ai/docs/search/highlights), [Exa search quickstart](https://exa.ai/docs/search/quickstart)). The tool name and output carry no Exa vocabulary, so another provider can sit behind it later. Rejected: Exa's MCP server over stdio with `ENABLED_TOOLS=web_search_exa` ([exa-mcp-server README](https://github.com/exa-labs/exa-mcp-server/blob/main/README.md)); it needs no code, but Exa names and shapes the tool, the MCP adapter forces `replay: "unsafe"`, and prod gains an `npx` child process.
  - **Fetch** is `web_fetch`: Node's `fetch` gets the HTML, linkedom parses it, and `Defuddle(document, url, { markdown: true })` from `defuddle/node` returns the main content as markdown ([Defuddle README](https://github.com/kepano/defuddle/blob/main/README.md), Node.js section). Only `http` and `https` URLs. Rejected: the `defuddle` CLI as a child process, which starts a process per call and must be on prod's PATH.
  - **Credentials.** The Exa key is `exa.apiKey` in soma's config file, as `anthropic.apiKey` is, and the chmod 600 warning (`src/config.ts:113`) extends to it; `EXA_API_KEY` overrides it. Without a key, `web_search` is not registered and soma starts normally. The key never appears in tool output or logs.
  - **Limits.** `web_search` returns 5 results by default and at most 10. `web_fetch` cuts the markdown at 20,000 characters and says it did. Both time out after 15 s, but the timeout covers only the request: `web_fetch` then parses, which cannot be aborted, so it reads at most 512 KB of the page and says when it read less. Dense 512 KB parsed in 1.7 s and dense 1 MB in 4.8 s, while a 416 KB GitHub page lost its README at 256 KB (measured 2026-10-27; see `FETCH_MAX_BYTES`). A worker thread would make parsing abortable; the human chose the cap. Since card `dense-page-blocks-event-loop` (2026-11-10) the parse runs on one worker thread (`src/core/extensions/web/parse.ts`), so the event loop, which Telegram polling, the web page and other turns share, is not held while a page parses: with a generated dense 512 KB page parsing, a 10 ms timer still fires within 100 ms. The worker starts with the first page and stays, since loading Defuddle for every page cost about as much as parsing a small one; it keeps the process alive only while a page waits, takes pages one at a time as the event loop did, and one that dies fails the pages it held and is replaced by the next page. It is still not aborted, so the tool's results and errors are as before. Every failure is an `isError` result the model can read, as the MCP adapter's are.
  - **Local addresses are not blocked.** `web_fetch` can read localhost and LAN addresses; the human does not count this as a risk for a single-user soma.
  - **Replay is `safe` for both.** pi-durable reruns a call after a crash only when it is declared safe (`node_modules/@earendil-works/pi-durable/README.md:277`), and a read has nothing to repeat.
  - **No deferred tools yet.** soma defines 18 tools of its own; two more do not change the plan in "External dependencies" (MCP) to defer tools and install `createToolSearchExtension()` once shikigami-bridge's tools arrive.
- **soma gets a web interface and a desktop assistant, both with a visible character.** This reverses the 2026-10-22 order (rich messages, then a Mini App), because the human wants three things Telegram cannot give: a character that keeps them company and reacts to the agents, reading that is not bound by a message format, and voice. Telegram stays, and the push target rules of 2026-10-23 cover the web as one more interface.
  - **One frontend.** The phone opens the page soma serves; the desktop assistant is a shell that loads the same page, so the character and the pages are written once.
  - **The desktop shell lives in this repo, in `desktop/`, and is not part of the release.** A release needs no build step ("Resident service"), and any desktop shell needs one, so the shell is packaged on its own. shikigami is not reworked into a client; its brain is the third brain "The problems to solve" names.
  - **Tailscale only.** The page is not public, so the first step needs no login of its own.
  - **A new character**, not shikigami's avatar: a fox, with every piece of art produced by code, never in an editor or by a commissioned artist. The rendering technology is three.js, picked by throwaway prototypes (M7 step 2) because the den should be able to become 3D.
  - **A creature in its own space, not a chat window.** The human wants the page to feel like a living thing talking from its den rather than a conversation log, so the fox's words fade, the human's typed words do not stay on screen, and state shows as objects in the room and actions of the fox (M7 steps 3 to 6). The room is one scene with a flat 2D view and a turnable 3D view, and the fox is paper-cut, flat slabs that read like a pop-up book from the side, both chosen by the human on 2026-10-27.

Decided 2026-11-03:

- **soma reads and writes the human's Obsidian vault through the obsidian CLI, as core extension tools.** This widens the 2026-10-27 exception from read-only tools to vault access, decided with the human for the `vault-read` and `vault-write` cards. The CLI is already prod's path to the vault for `open_card` (`src/adapters/obsidian/card.ts`), its search uses Obsidian's own index, and it needs the Obsidian app running on the machine. Rejected: plain file I/O on the vault folder, which works with the app closed but has no index search and leaves links stale on a rename; and a third-party Obsidian MCP server, which goes through the Local REST API plugin and makes every tool replay-unsafe.
  - **Reading** (`src/core/extensions/vault/`): `note_search` and `note_read`, both `replay: "safe"`, return the note's path and text inside the observed-content fence of the memory section. The fence's own markers are dropped from the text until none is left, so a note cannot end the fence. A note is cut at 20,000 characters, as `web_fetch` is. An empty path is refused, because the CLI reads the note open in the app when it gets none. The CLI exits 0 on a failure and prints it where the answer would be, so the adapter checks each answer's shape: `file` before `read`, since `read` prints a note that begins with "Error:" the same way as a failure (`src/adapters/obsidian/vault.ts`).
  - **Writing**: `note_create`, `note_append` and `journal_append` create and append only; no tool overwrites or deletes. The vault is a git repo that obsidian-git commits every 30 minutes, so git history is the undo. A write asks no confirmation. Every write except one into today's journal then appends `- <summary> [[note]]` to that journal, as the vault's own `AGENTS.md` asks, and the tools tell the model to name what it wrote. All three are `replay: "unsafe"`: after a crash the model is told the call may have partly run, rather than an append landing twice. `Readwise/` is never written, since its plugin overwrites it; reading it stays open. The adapter works around three CLI behaviours: `create` on an existing path makes `<name> 1.md` instead of failing, so it checks the path first and requires the answer `Created: <path>`; a missing heading on `append` answers `Error:` with exit 0; and the CLI turns the two-character sequences `\n` and `\t` into a line break and a tab with no escape, so text holding them is refused. `daily:append` creates the day's journal when it does not exist yet, as prod's first write of 2026-11-09 showed.
  - **Denied folders.** `vault.deny` in soma's config names folders soma neither reads nor writes; the human set `Clippings`, the folder of web clippings, the likeliest carrier of injected instructions. Folders compare case-insensitively, after the path is normalized as Obsidian's `normalizePath` does for `create` (trimmed, `\` as a separator): the CLI looks up a path to read or append exactly, but `create` normalizes it, and its new file name is chosen case-insensitively. Known gap: a case variant of an existing note passes the exact `file` check, and `create` then makes `<name> 1.md` and fails on its answer. Without `vault.name` the tools are not registered.

The scope, what soma will never do to one, and the three milestones are in "Foreign agents".

Decided 2026-11-17:

- **soma writes its dispatch list to `<db>.jobs.json` as the read interface for local programs, until a socket replaces it.** Decided with the human for the `dispatch-jobs-sidecar` card, the first milestone of making the agent-tree terminal dashboard a soma interface; reading comes first and dispatching from the dashboard is the second. Why a file: the only out-of-process interface is the web page's WebSocket, which accepts one tailnet Host and Origin and, in serve mode, trusts the login header `tailscale serve` adds, so a program on the same Mac could use it only by forging them; the client socket of M4 is not built. The dashboard already polls muster's `phase.json` every second, and a file fits that. A socket or WebSocket may follow once this is in use, and the file goes then.
  - **What it is.** `{ version: 1, jobs: [...] }`, one entry per job with `card`, `agent`, `sessionId`, `status` (the state name), `kind` (the blocked kind, else null), `outcome`, `repo`, `created` and `updated`; the shape is `JobEntry` in `src/core/domain/dispatch.ts`. A reader of another `version` must not guess. It never holds `launch`, `ticket`, a status's message or options, or a decision's words, which carry the card's text or the agent's.
  - **When.** `keepJobsFile` (`src/core/extensions/dispatch/sidecar.ts`) watches the dispatch list document, writes once at startup from the stored list, and writes again whenever what the file shows changes. It is written to a temporary file and renamed over, mode 0600, by an adapter (`src/adapters/jobs/jobs-file.ts`) that takes plain JSON, next to the other sidecars. A write that fails is logged and the next change tries again.
  - **Repo and times.** `Job` gained `repo` and `createdAt`, set when the job is recorded. A job recorded before that shows `repo` and `created` as null. The file has no `worktree` field: the agent port's `start` does not return the path, herdr picks its own place and rex, ACP and tty reuse a `fleet/<card>` branch already open elsewhere, so soma could state it only by asking git on every write, and a path derived from `repo` and `card` would often be wrong; a reader such as the dashboard reads each agent process's cwd itself. `updated` is when the entry last changed: no job field is stamped at every one of the many places that change a job, so the writer compares each entry with the one it wrote last, read back from the file after a restart, and stamps the time only when they differ. A job with no earlier entry, as after the file was deleted or could not be read at startup, is stamped with the time the writer first sees it, whether or not it has `created`, since nothing says when it last changed.
- **`soma dispatch --repo <path> <card>` starts a job from host code, with no turn of the model.** Decided with the human for the `host-dispatch-cli` card, the second milestone: the human picks a card in the agent-tree dashboard, and soma dispatches it the way muster dispatches a worker. Built 2026-11-18.
  - **Path.** `bin/soma dispatch` (`src/dispatch-cli.ts`) sends `{ kind: "dispatch", repo, card }` as one JSON line over the defer socket (`src/adapters/defer-socket/`), the one the config's `deferSocket` names; it does not read `SOMA_SOCKET`, as `soma defer` does; `--repo` is resolved against the directory the command runs in. `hostDispatcher` (`src/core/extensions/dispatch/host.ts`) runs the dispatch tool's own steps, `startJobIn` in `src/core/extensions/dispatch/index.ts`, with `conversation.commit` in place of the tool's api, so the order of "Idempotent dispatch" holds: the dispatch list, then the agents listed, then the start, then the job's commit. The job stores the card's launch prompt, which the event bridge sends at the agent's first idle, as for any job. Nothing is told to the human when it starts; the job shows in `<db>.jobs.json` and in later reports as any job does. Card status and `blocked_by` are not checked, as the tool does not check them.
  - **Trust is the defer socket's.** Any process of the same user that can open the 0600 socket may dispatch, as it may defer ("Agent-deferred instructions"); there is no chat gate and no token. A second socket was rejected: it would have the same mode and the same reach, since an agent runs as that user and can read the config too, and it would add a path, a key and a server. A request with no `kind` is a defer, since the CLI of an older release, still on the `PATH` of an agent it started, sends none.
  - **An agent soma dispatched may not dispatch (decided with the human, 2026-11-18).** Review found that the CLI took `SOMA_SOCKET` first, so any agent soma started could start more jobs with no human in the loop, bounded only by the hangar cap. soma sets `SOMA_AGENT=<card>` on every agent it starts, so `soma dispatch` refuses when it is set and not blank: `soma dispatch: not dispatched: an agent soma dispatched cannot start jobs (SOMA_AGENT=<card>)` on stderr, exit 1, nothing sent, before the arguments or the config are read. The CLI also sends the caller's `SOMA_AGENT`, when it has one, as `agent` in the request, and the server refuses a dispatch request that carries a non-blank one with the same reason and records nothing; a request with no `agent`, from an older CLI, is served as before. The CLI no longer prefers `SOMA_SOCKET`: it finds soma by the config's `deferSocket`, as for a human. **The limit: this is a cooperative check, not a security boundary.** It stops an agent that runs `soma dispatch` as given. An agent that clears `SOMA_AGENT`, or reads soma's config for the socket path and writes the request to the socket itself with no `agent`, gets through, since the socket cannot tell it from the human ("Trust is the defer socket's"). The human accepted that; closing it would take an identity the socket can check, which it does not have.
  - **The repo.** The config's `reposDir` (`SOMA_REPOS_DIR`, absolute) names one folder; `repoUnder` (`src/adapters/repos/folder.ts`) takes a repo only when its realpath is a direct child of the folder's realpath and holds a `.git` directory or file, so neither a link nor `..` reaches past the folder. The job records that real path. With no `reposDir`, every dispatch is refused. The dashboard reads `reposDir` from soma's config to offer the folders under it.
  - **Replies.** A started job, a card that already had one (returned as it is, whatever repo it runs in), or an agent of the card's name found running (recorded without a second start) print on stdout with exit 0. A name that is not a card's file name, a repo the check refuses, a card that cannot be read, a ticket job holding the name, and a start that throws, such as a full hangar, are refused on stderr with exit 1, and no job is recorded. A usage error exits 2.
  - **Session id and crash recovery.** No tool call means no `memo`, so the session id is stored in its own document (`HostSessions`, kind `soma.dispatch.host-sessions`) before the start and dropped in the commit that records the job. A crash between `agents.start` and that commit leaves the agent running with no job: the next `soma dispatch` of the card finds it listed and records it under the id it was started with, which herdr cannot list until claude reports it. Nothing recovers it at startup; until the rerun, the agent shows as a foreign one and gets no launch prompt. The CLI says so when a reply is lost: unlike a second defer, a rerun is safe. Dispatches of one card in one process, the tool's and the host's, run one at a time, so a dashboard that fires twice starts one agent.


## Open questions

1. **(Decided, 2026-10-18) How dispatch connects to herdr.** There are three ways:
   - **(Suggested for M1) Call cc-mobile's existing `POST /api/launch`.** This route, in order, validates the bearer token, checks, queues, creates the worktree (`launch.ts:196`), checks again (`:212`), creates the session, writes the binding file and sends the prompt (`server/launch.ts:196-349`). The benefit is that soma copies no code, the concurrency cap is shared naturally, and the obw write-back hook should work as usual (not traced). It has two costs: soma depends on the cc-mobile process being up, while M4 makes cc-mobile a client of soma, and neither process may have its startup stuck on the other; and dispatch is per obw card, so ad-hoc work without a card cannot go this way.
   - **Copy the pure functions into soma**, noting the source commit. The cost is that the two copies of the code will diverge, and the concurrency cap must be coordinated separately.
   - **Extract a shared package** that both depend on. This is the cleanest, but cc-mobile must change first, so it suits M4.

   Reading status and reading transcripts do not go through the dispatch route, so M1's event bridge still needs herdr's connection and subscription code.

   Decided on 2026-10-18: in M1 the herdr adapter dispatches directly into the `fleet` hangar session instead, opening the `fleet/<card>` branch with herdr's own `worktree.create` and then calling `agent.start` with `--session-id`. The reason is that `/api/launch` would require soma to hold cc-mobile's launch token and depend on cc-mobile being up, while the herdr adapter has to be written anyway; the concurrency cap counts the agents running in the hangar with cc-mobile's formula, so both sides count the same set. `/api/launch` is kept as another implementation of AgentPort (cancelled on 2026-10-24; see "Decisions made").
2. **Which machine shikigami runs on.** If it is the same machine as the core, it connects locally; if it is on the laptop, it connects over Tailscale, the same way the phone connects to cc-mobile.
3. **Where reports are stored, and whether there should also be a daily summary.** The ten-minute short report is written into a `notice` record and delivered by the adapters; whether to also write it into the Obsidian vault's journal or the matching obw card is undecided.
4. **How to dispatch ad-hoc work without an obw card.** `POST /api/launch` is per card; either soma first creates a card for the ad-hoc work, or it takes its own dispatch path. Since `/api/launch` was cancelled on 2026-10-24, only the latter two remain, and the dispatch tool is also per card for now.
5. **(Decided, 2026-10-18) Which MCP server to use for email and calendar, and where the credentials go.**

   Decided on 2026-10-18: use [workspace-mcp](https://github.com/taylorwilsdon/google_workspace_mcp) (MIT, not archived, v2.1.0 released on 2026-10-09), one stdio server that provides both Gmail and Calendar, signing in to a personal account with Google OAuth. The launch command is `uvx workspace-mcp@2.1.0 --single-user --permissions gmail:readonly calendar:readonly`. On 2026-10-18 it was actually started through soma's bridge, and `tools/list` listed only read tools, among them `search_gmail_messages` (`query` goes straight to Gmail, so `is:unread is:important` works) and `get_events` (`time_min`, `time_max`). Every tool has a `user_google_email` parameter. With only `--single-user` this parameter is still required, and passing an account not in the credentials directory fails outright rather than falling back to other credentials (the single-user branch of `auth/google_auth.py` in workspace-mcp 2.1.0). So `env` must also set `USER_GOOGLE_EMAIL`, and the server then makes the parameter optional and fills in this account (the `USER_GOOGLE_EMAIL` handling in `core/server.py`; on 2026-10-18 a test through the bridge showed that `required` in `tools/list` no longer includes it).

   Credentials stay out of the repo. soma reads `~/.config/soma/mcp.json` (the path can be overridden by the environment variable `SOMA_MCP_CONFIG` or the configuration file's `mcpConfig`), in the format `{"servers": {"<name>": {"command", "args", "env"}}}`. The server's own credential paths go in `env`: the OAuth client uses `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` (or `GOOGLE_CLIENT_SECRET_PATH` pointing at client_secret.json), the token directory uses `WORKSPACE_MCP_CREDENTIALS_DIR`, suggested as `~/.config/soma/google`, and the account uses `USER_GOOGLE_EMAIL`. While the Google OAuth app stays in Testing mode, the refresh token expires after seven days ([google-calendar-mcp README](https://github.com/nspady/google-calendar-mcp)); it must be published to production to avoid re-authorizing every week.

   Candidates not chosen:
   - Google's official [Gmail](https://developers.google.com/workspace/gmail/api/guides/configure-mcp-server) and [Calendar](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server) MCP servers are still in Developer Preview, with Streamable HTTP only, and whether a personal account can join is unverified. They can be adopted after general release; the bridge must first add HTTP and OAuth.
   - [@cocal/google-calendar-mcp](https://github.com/nspady/google-calendar-mcp) plus [@klodr/gmail-mcp](https://github.com/klodr/gmail-mcp) are two Node servers whose credentials must be set up separately; the latter has only one maintainer.
   - [GongRzhe/Gmail-MCP-Server](https://github.com/GongRzhe/Gmail-MCP-Server) is archived.
